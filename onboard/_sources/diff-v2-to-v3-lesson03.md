## Critical

- **KVA-v2-001 — APPLIED** (and it was a real defect, not a nuance). The caption under `helm repo add` claimed the chart-repo add is "the only step in the module that talks to the internet". The guide says otherwise in its own words: for environments connected to the internet, one needs access to **three** repositories to install Veeam Kasten — the Helm repository containing the chart, the container registry containing the Veeam Kasten container images, and upstream repositories for dependencies such as Prometheus [Src: Kasten Docs 9.0.2 p.149] — and all images for a default install are hosted at `gcr.io/kasten-images` [Src: Kasten Docs 9.0.2 p.8]. Four edits landed: (1) the caption now says "this is the chart repository only — one of three places an internet-connected install reaches out to"; (2) a new **"Check this before the install window"** caution in Section 1 states the three-repository fact, the registry host, the private-registry option for air-gapped installs [Src: p.149], and the failure signature (a blocked registry path fails neither the repo-add nor the install command — it surfaces as pods that never reach Running); (3) a fourth hero prerequisite, *Image-pull reachability*; (4) a ninth, **blocking** readiness-checklist item — "The cluster nodes can pull the Veeam Kasten container images" — so the gate the implementer actually needs is in the gate list, not only in prose. The checklist lede now reads "Six items are blocking", and the verdict JS was changed from the hard-coded "all eight items confirmed" to `boxes.length`, so the widget no longer contradicts itself when items are added. Its blocking-verdict line now reads "The primer tool answers the Kubernetes, CSI and annotation items for you; the registry path is yours to confirm" — the primer's three operations [Src: p.7] do not include registry reachability, so the checklist no longer implies the tool covers it.
- **KVA-v2-002 — ADJUSTED, and the `[VERIFY]` resolved rather than shipped.** The row was right that the Veeam Repository field list had no authentication step, and the source answers the question outright: **Provide access credentials in the Username and Password fields** [Src: Kasten Docs 9.0.2 p.337]; **Ensure Access Permissions are granted within VBR for the specified account (or related security group) and backup repository** [Src: Kasten Docs 9.0.2 p.338]. Two new paragraphs in "Pointing it at a Veeam repository" carry those facts plus the submit-time behaviour the implementer will hit next: the dialog validates the input data on Submit, communication with the server uses SSL and requires the server's certificate be trusted by Veeam Kasten, and the **Skip certificate chain and hostname verification** option disables certificate validation [Src: p.338]. The destination table's Veeam Repository row also gained "plus access credentials in the Username and Password fields [Src: p.337]" so the table and the walkthrough agree. The account-preparation work is framed as a Veeam Data Platform-side pre-implementation task, which is the row's real ask — the implementer no longer has to guess whether to create a Veeam Backup & Replication account first.
- **KDO-v2-003 — ADJUSTED.** The Director's read is correct: "not advisable if granular access is needed" understates a mode with no authentication at all. The guide's clause stays verbatim (it is the source's own wording and the quiz depends on it), and the cell now opens with "No authentication method is configured" and closes with the consequence spelled out: read "all operations" literally, it includes the destructive ones, and with no authentication configured there is no authenticated identity behind any of them — treat Direct Access as lab-only, not the exposure choice on a cluster whose restore points you would have to account for. Two changes from the proposal: "including deleting a restore point" became "the destructive ones" (the guide says "all Veeam Kasten operations"; naming one specific operation the source does not name is an unnecessary inference), and "no authenticated identity to record against the action" became "no authenticated identity behind any of them" — the guide makes no statement about what is or is not recorded in an audit log, so the claim stays on what follows logically from "no authentication configuration" [Src: p.220]. Knock-on edit of my own: the Direct Access distractor rationale in knowledge-check Q3 was rewritten to match, so the quiz no longer teaches the softer framing the row objected to.

## Significant

- **KVA-v2-003 — APPLIED.** "As specified elsewhere" now points somewhere for every platform this audience runs, under a new sub-heading after the AWS block: Azure service-principal credentials [Src: p.39]; Google Cloud's two Service Accounts and the `roles/compute.storageAdmin` role [Src: p.79, p.83]; vSphere CSI credentials via Helm parameters or a vSphere Infrastructure Profile [Src: p.91]; OpenShift's `--set scc.create=true` for the SecurityContextConstraints [Src: p.55]. Two runnable additions: the guide's full Azure service-principal `helm install` command, and the vSphere credential flag trio — both quoted as exact multi-line blocks that exist verbatim in the source, so the module now has something to copy for the two most likely non-AWS cases.
- **KVA-v2-004 — ADJUSTED, `[VERIFY]` resolved.** The guide publishes no htpasswd invocation, so a `[VERIFY]` would have sent the Architect after something that is not there. What the source does specify is the *shape* of the string, which is the thing that actually goes wrong: htpasswd credentials in the format `username:hashedpassword`, generated with an online tool or the htpasswd binary found on most systems, then used to log in to the dashboard [Src: Kasten Docs 9.0.2 p.45]. The paragraph now says plainly that no invocation is published ("do not go hunting for one"), gives the format, and points at the already-quoted flag example as the form to compare output against. The secret alternative gained the missing detail: the secret must be created with the key named `auth` and the value as the password generated using htpasswd in the data field [Src: p.221].
- **KVA-v2-005 — APPLIED.** `Missing deletionPolicy, using default` now carries a verdict: read it as information, not a finding to clear. It carries no `- OK` because it reports a state rather than passing a test, and the state is acceptable — the guide calls the default deletion policy the default and recommended one [Src: p.102], and the release notes record that a `Retain` deletionPolicy for VolumeSnapshotClasses is no longer required or recommended [Src: Kasten Docs 9.0.2 p.1153]. The paragraph closes by naming the line that *is* a stop condition: the annotation line above it [Src: p.103].
- **KVA-v2-006 — ADJUSTED; the one deliberate `[VERIFY]` in this build.** "Go to the support docs" is now backed by a documented first action: a new "If pods do not reach Running" sub-section quotes the debug script the guide asks you to run as a first step to get information to support, with the archive it produces (`k10_debug_logs.tar.gz`) and the System Information page alternative [Src: Kasten Docs 9.0.2 p.862]. A "Before you tear it down" caution covers the removal path the row asked about: uninstall with the Helm command so non-namespaced resources are cleaned up (`helm uninstall k10 --namespace=kasten-io`), not `kubectl delete namespace`, which might cause issues with stale services; CRDs remain afterwards and deleting them may lead to data loss [Src: p.865]. The row's actual question — is it safe to uninstall and re-run mid-install, or must the namespace / catalog PVC be cleaned first — is **not answered anywhere in the 9.0.2 guide**, so it ships as `[VERIFY: whether the kasten-io namespace and the catalog persistent volume claim must be removed before re-running helm install after a failed install …; Architect to confirm before a learner is told it is safe]`, with interim guidance to treat a stuck install as a support case with logs attached rather than a retry loop. I will not invent a safe-retry procedure for a first-time implementer on a production cluster.
- **KDO-v2-008 — ADJUSTED.** The immutability toggle was one conditional clause inside a dense five-sentence paragraph; it is now its own paragraph with a bolded lead-in ("Immutability is a toggle, and it belongs on by default"), which is the surfacing the row asked for without inventing a new component. The source claims are unchanged [Src: p.315, p.341]. Two wording changes from the proposal: "Kasten Disaster Recovery" → "Veeam Kasten's own disaster recovery" (naming rule — "K10" and bare "Kasten" product names only appear in verbatim technical strings), and "the first thing a CISO will flag" was kept but paired with "an auditor", plus the practical point that "the bucket was not locked" is a procurement decision you want on the record before the review. Governance framing, no new product claim.

- **KVA-v2-010 — ADJUSTED.** The proposal asserted a prerequisite the guide does not state in those terms; there is no network-requirements or firewall section in the 9.0.2 guide to cite. The new paragraph before "What you can point it at" frames the check as the Veeam Data Platform habit it is, and names the symptom — a firewalled endpoint, unresolvable DNS name or closed API port arrives as a failed validation on the profile card, not as an obvious network error.
- **KVA-v2-011 — APPLIED.** A caption under the pod-watch command: `--watch` streams status changes and holds the terminal open rather than returning you to the prompt — that is the command working, not hanging — read until every pod shows Running, then Ctrl+C. - **KVA-v2-012 — APPLIED.** The vSphere case now has a path, not a shape: a new "The vSphere profile, in full" block gives the required fields (vCenter Server as IP or hostname, vSphere User, vSphere Password) [Src: p.123], the precedence rule an implementer needs — install-time vSphere credentials are ignored in favour of the credentials in the Infrastructure Profile [Src: p.123] — and the complete vCenter permission set for a dedicated Veeam Kasten account: Datastore (Allocate space, Browse datastore, Low level file operations), Global (Disable methods, Enable methods, Licenses), Virtual Machine Snapshot Management (Create snapshot, Remove snapshot, Revert to snapshot), Cryptographic operations → Decrypt on 8.0, plus CNS → Searchable for vSphere with Tanzu, assigned on the root vCenter object and the datacenter objects propagating down each subtree [Src: p.124]. - **KVA-v2-013 — ADJUSTED; one sub-part deferred with reason.** The hero meta cell now reads "~40 minutes / reading time" rather than "estimated", and a new hero paragraph states that executing the runbook is a separate booking, naming the two things that dominate elapsed time with citations: the deeper CSI check writes data, snapshots it, provisions a new volume from the snapshot and validates the data [Src: p.102], and after the install it may take a couple of minutes for all pods to come up [Src: p.100]. It closes by telling the learner to time the pre-flight pass in their own environment and size the change window from that. **Deferred:** the row's request for a concrete execution-time range (e.g. "45–90 minutes against a healthy cluster"). No such figure exists in the 9.0.2 guide, and elapsed time here is dominated by the customer's storage performance and change-control process — inventing a range would be exactly the kind of plausible-sounding number the pipeline exists to keep out, and planning a change window off a fabricated figure is worse than planning off an honest "time it yourself".

## Net change

Lesson 03 stops being a runbook that only works when the network is open and the platform is AWS. The three critical rows all landed on real gaps: an implementer in a restricted network is now told before the install window that an internet-connected install reaches a container registry as well as a chart repository [Src: p.149, p.8] — with a blocking checklist item to gate on — and the module no longer tells them the opposite; the Veeam Repository location profile now shows the Username/Password fields and the Veeam Backup & Replication access-permission prerequisite that the field list was silently missing [Src: p.337, p.338]; and Direct Access is characterised as the lab-only posture it is rather than a granularity preference.

The significant rows closed the "what do I do now" holes: non-AWS platforms have runnable credential paths (Azure and vSphere as exact quoted blocks, GCP and OpenShift as named roles and flags), the ambiguous `Missing deletionPolicy, using default` line has a verdict, the htpasswd step has the string format the guide actually specifies instead of a dead end, and a failed install has a documented first action (collect logs) plus a documented removal path — with the one genuinely unanswered question left as a visible `[VERIFY]` rather than a confident guess. The minor rows closed comprehension and governance gaps: GitOps is glossed, Kopia's trio is anchored to something the learner already owns, the vSphere Infrastructure Profile is complete down to the vCenter privilege list [Src: p.123, p.124], Multi-Cluster Manager is a signpost instead of a footnote [Src: p.1012], destination reachability is a stated pre-check, `--watch` no longer looks like a hang, and the time estimate no longer reads as an execution estimate.

Structure is intact: 9 rail dots, 6 sections plus knowledge check and recap, 7 Continue gates, 5 questions × 3 options with rationales, readiness widget verified in-browser (9 items, 6 blocking, dynamic verdict). Kit components untouched apart from the readiness widget the rows explicitly targeted.

**Gates (final run):** `lint-voice` 0 errors, 8 warnings (identical count and character to the v2 baseline — 5× `repo` inside verbatim `helm repo add` / `repo.example.com` strings, 1× pre-existing `actually`, 2× heuristic false positives on quoted primer output and a table header, 1× lightbox `alt=""`). `smoke-test-html` exit 0. `verify-quotes` 94/94 quotes verbatim in source (was 73/73 — 21 new quoted strings, all verified).
