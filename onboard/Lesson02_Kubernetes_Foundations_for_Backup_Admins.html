Orientation · 01

Same job, unfamiliar machinery

This section sets the contract for the rest of the module: which of your existing instincts transfer to Kubernetes, which ones will actively mislead you, and the four questions every concept below gets answered against. Read it and you will know how to read everything that follows.

Your job description does not change. You still need to know what exists, decide what is protected, prove it is protected, and get data back when someone deletes the wrong thing. What changes is the shape of the thing you are protecting. In a vSphere estate the unit of protection is a virtual machine: a long-lived object with an identity, a set of virtual disks, and a place in an inventory tree. In Kubernetes the unit of protection is an application — a set of running processes plus the configuration that describes them plus, sometimes, the volumes they mounted. The running processes are disposable by design. The configuration and the volumes are not.

That single shift explains most of what feels strange later. It is why "restore the machine" is rarely the right recovery request, why the interesting objects are the ones nobody sees in a monitoring dashboard, and why the storage layer matters more here than it does in a VMware-centric backup design.

Three ideas to hold on to

Everything in this module hangs off these. If a later section stops making sense, come back here.

01
Kubernetes runs on desired state, not on instructions.
You declare what should exist; the control plane keeps reality matching that declaration. Nobody powers a workload on by hand.
02
The compute is disposable; the data and the definitions are not.
A replacement process is one reconciliation away. A deleted volume, or the manifest that described the application, is not.
03
The application is the unit of protection.
Veeam Kasten works at that level: it discovers applications on the cluster it runs in and protects them as whole objects — stateful and stateless parts togetherApplication objectVeeam Kasten's application object encapsulates information about all stateful and stateless resources that make up the application [Src: Kasten Docs 9.0.2 p.620]..
The analogy contract

Every concept below is introduced four ways, in this order: what it is, the closest thing you already administer, where that comparison breaks, and what it means for backup. The third part is the one that matters. An analogy you trust past its limit is worse than no analogy at all, so each one is retired out loud rather than quietly stretched.

Remember

You are not learning Kubernetes in order to develop on it. You are learning the parts of it that decide what gets backed up, what a restore can put back, and what the storage layer is capable of. That is a much smaller subject than "Kubernetes", and it is the whole subject of this module.

Cluster · 02

The cluster, the control plane, and the nodes

By the end of this section you'll be able to point at the three layers of a cluster, say which one you talk to and which one runs the work, and explain why the vCenter Server plus ESXi host picture gets you about 70% of the way there before it starts costing you.

A cluster is the whole unit: a set of machines that pool their compute and present one API. A node is one of those machines — physical or virtual — that runs the workloads. The control plane is the set of components that hold the cluster's desired state, decide which node each workload lands on, and continuously reconcile what is running against what was declared. Placing work on a specific node is not something you do by hand. You submit a description of what you want to the API, and the control plane schedules it.

The command-line client you will see in every Kubernetes procedure — kubectl — is nothing more than a client for that API. It is closer to PowerShell against a management server than to a console session on a host. There is no node-level UI you log into to fix a workload, and no per-node inventory you browse to find one.

Where the comparison holds

One place to ask about everything
The cluster API plays the role vCenter Server plays: a single authority you query for what exists.
Compute you scale out
Nodes are added and drained much as hosts are added and put into maintenance mode.
Placement is somebody else's problem
You express intent; something else picks the host. That instinct transfers.

Where it breaks — and what it costs you

01
There is no per-node object worth protecting.
Protecting a node is not a meaningful goal. Nodes hold no unique application state you can restore from.
02
The control plane is not your backup target either.
Veeam Kasten is built to protect Kubernetes applications and cannot be used to deploy or restore a cluster's overall state, so cluster build-out stays with your infrastructure-as-code tooling [Src: Kasten Docs 9.0.2 p.1090].
03
Nothing waits for you to fix it.
Delete a running workload and the control plane may well recreate it before you finish reading the alert. That is healing, not recovery — the data question is still open.
Heads up

The word "cluster" means something different on each side of this comparison. A vSphere cluster is a grouping of hosts inside a larger inventory. A Kubernetes cluster is the entire management domain — its own API, its own accounts, its own set of nodes. Two Kubernetes clusters are two separate worlds, which is exactly why moving an application between clusters is treated as a restore operation rather than a migration wizard [Src: Kasten Docs 9.0.2 p.1090].

Workloads · 03

Pods, Deployments, and StatefulSets

By the end of this section you'll be able to say what runs (a Pod), what keeps it running (a Deployment or a StatefulSet), and which of the two tells you at a glance that there is data underneath worth protecting.

A Pod is the smallest thing Kubernetes runs: one or more containers that share a network identity and a lifecycle. Pods are created and destroyed constantly — by upgrades, by scaling, by a node going away. You do not repair a Pod; something replaces it. Nothing inside a Pod's own filesystem is expected to survive that replacement.

Because Pods are disposable, you rarely create one directly. Instead you declare a controller that owns them. A Deployment says "keep this many identical, interchangeable copies running" — right for a web front end, an API tier, anything where copy three is indistinguishable from copy one. A StatefulSet says "keep these copies running, each with a stable name and its own storage" — right for a database, a message broker, anything where copy three has its own data and is not interchangeable with copy one.

01

Pod

Flip ↻

One or more containers running together with a shared network identity. Replaced rather than repaired, and renamed when it is replaced. Closest instinct: a running process group, not a VM. For backup: a Pod is evidence that something is running, not the thing you restore.

02

Deployment

Flip ↻

A controller that keeps a declared number of interchangeable Pods running and rolls them over during upgrades. Closest instinct: a template plus a policy that maintains the fleet. For backup: what matters is the declaration, not the copies it produced.

03

StatefulSet

Flip ↻

A controller for Pods that each keep a stable identity and their own persistent volume. Closest instinct: the tier of the application you would have given its own dedicated disks. For backup: this is where your attention goes — a StatefulSet is a strong signal that volumes with data are present.

Why the stateful ones are the ones you protect

Rebuild a stateless front end from its declaration and you have lost nothing. Rebuild a database from its declaration and you have an empty database. That asymmetry is the entire reason a Kubernetes backup product exists, and it is visible in how Veeam Kasten presents a cluster: its dashboard can filter down to only the applications that have stateful services, which it defines as applications containing a persistent volume [Src: Kasten Docs 9.0.2 p.301].

Veeam Kasten classifies Pods, VirtualMachines, StatefulSets, Deployments, and DeploymentConfigs as workloads, and treats an application as something made up of multiple Kubernetes resources and workloads together [Src: Kasten Docs 9.0.2 p.303]. So a single application card in its dashboard may account for several volumes, several network resources, several workloads, and additional configuration objects at once [Src: Kasten Docs 9.0.2 p.303].

Heads up

Do not read "StatefulSet" as "everything with data". Some modern data services are managed by their own custom controllers rather than by a StatefulSet, and Veeam Kasten added support for pre- and post-snapshot Blueprint actions for those custom-resource-managed workloads by mapping Pod and volume-claim ownership when a policy runs [Src: Kasten Docs 9.0.2 p.1096]. The reliable signal that data is present is a persistent volume, not the controller type.

Pro tip

A crash-consistent volume snapshot is not always enough for a database, exactly as it is not in a virtual estate. Veeam Kasten handles that case with Kanister Blueprints, which run pre- and post-backup hooks for workloads that need application-specific work such as pausing a database before a backup or migration [Src: Kasten Docs 9.0.2 p.1090]. You will meet these again when you build policies.

Namespaces · 04

Namespaces: where an application lives

By the end of this section you'll be able to explain what a namespace groups, why Veeam Kasten treats one as an application, and how that default changes the way you will scope a protection policy compared with picking objects out of an inventory tree.

A namespace is a named boundary inside a cluster that holds a set of related objects — workloads, configuration, secrets, storage claims, service definitions. Names are unique within a namespace rather than across the cluster, access control is commonly granted per namespace, and a team is commonly given one to work in. (On Red Hat OpenShift, which this course also targets, the same boundary surfaces as a Project — Veeam Kasten's own OpenShift install instructions treat the two words as one thing, telling you to create "a project (namespace)" for the installation [Src: Kasten Docs 9.0.2 p.67].) In practice a namespace is how an application is deployed: one namespace, one application, all of its parts inside it.

That convention is load-bearing for Veeam Kasten. The platform by default equates namespaces to applications — for ease of use, for consistency with Kubernetes practice and role-based access control, and because it mirrors the most common application deployment pattern [Src: Kasten Docs 9.0.2 p.301]. It is a default, not a cage: policies can be defined to operate on more than one namespace, or on only a subset of an application that lives inside a single namespace [Src: Kasten Docs 9.0.2 p.301].

The closest thing you know

As a container for related things
A folder in an inventory tree, or a tenant boundary you scope permissions to.
As a selection target
A folder you point a job at so that new objects inside it are picked up without editing the job.
As an access boundary
The level you delegate: this team administers what is inside, and nothing outside.

Where the folder comparison breaks

01
A folder is organizational. A namespace is functional.
Moving a VM between folders changes nothing about the VM. Objects do not move casually between namespaces — references, names, and access rules are all scoped to the one they are in.
02
Some of the application is not in the namespace at all.
Cluster-scoped objects such as StorageClasses and custom resource definitions live outside every namespace, and an application that depends on them needs a policy that protects both the application and its cluster-scoped resources [Src: Kasten Docs 9.0.2 p.429].
03
Deleting the namespace deletes the contents.
This is the accident you are protecting against, and it takes volumes and their snapshots with it. Section 06 explains why that detail decides whether a snapshot counts as a backup.
Why this is good news for you

Discovery is the part of onboarding a new estate that costs the most in a virtual environment: finding everything, deciding what is in scope, keeping the list current as people build things. Here the inventory maintains itself, and the interesting number on that dashboard is the unmanaged count — the applications that exist and are not yet covered by any policy [Src: Kasten Docs 9.0.2 p.301]. That number is your work queue.

Remember

Namespace is the noun you will think in from now on. When a colleague asks whether something is protected, the answer is a namespace and a policy — not a machine name.

Storage · 05

Volumes, claims, and storage classes

By the end of this section you'll be able to trace a request for storage from the claim an application writes to the volume that gets bound to it, name the component that does the provisioning, and explain why this layer sets the ceiling for your data protection design.

Three objects do the work. A PersistentVolumeClaim is the application saying "I need this much storage, of this class". A StorageClass is the named offering that claim asks for — the tier, the parameters, and which provisioner fulfils it. A PersistentVolume is the actual volume that gets created and bound to the claim. The application author writes the claim; the cluster produces the volume.

Doing the provisioning is the CSI driver — CSI being the Container Storage Interface, the standard contract between Kubernetes and a storage system. Your array vendor ships the driver; the cluster calls it to create volumes, attach them, and — when the driver has that capability — snapshot them.

STAGE 04
The bound volume

Stage 04 — the bound volume. The PersistentVolume exists as its own object with its own lifecycle, bound to the claim that asked for it and mounted into the Pod. This is the data. Everything Veeam Kasten does about that data — snapshot it, export it, restore it — happens through this object and the driver that created it.

What this means for backup

In a virtual estate the storage layer is largely an implementation detail of the backup design: the hypervisor presents disks, and your backup server reads them. Here the storage layer is a first-class dependency, because the ability to take a fast, consistent point-in-time copy belongs to the driver rather than to the backup product. Veeam Kasten supports direct integration with a set of storage providers — among them Amazon Elastic Block Store, Azure Managed Disks, Google Persistent Disk, Ceph, Cinder-based providers on OpenStack, vSphere Cloud Native Storage, Portworx, and Veeam Backup — as well as integration through CSI [Src: Kasten Docs 9.0.2 p.102].

Two practical consequences follow. First, a storage system with no CSI driver that can snapshot pushes you onto a file-copy-based path: Veeam Kasten supports Generic Storage Backups for such systems, and the documentation states plainly that this approach is not recommended [Src: Kasten Docs 9.0.2 p.1090]. Most NFS storage services on the market do not provide a CSI driver with snapshot and clone capabilities, and migrating persistent data to storage that does is the recommended course [Src: Kasten Docs 9.0.2 p.1090]. Second, snapshot limits are a design input: verify from your provisioner's documentation whether there is a cap on the total number of snapshots per persistent volume claim, because that cap constrains policy retention settings [Src: Kasten Docs 9.0.2 p.1090].

For a customer conversation

When a customer asks why the storage question comes up so early in a Kubernetes data protection design, the honest answer is the one above: the snapshot capability lives in their CSI driver, so the driver they chose sets the ceiling for how efficiently their applications can be protected. Establishing that before a deployment is far cheaper than discovering it during one.

Snapshots · 06

VolumeSnapshots, and why drivers differ

By the end of this section you'll be able to state the three conditions that let Veeam Kasten take CSI volume snapshots, explain in one sentence why a volume snapshot on its own is not a backup, and describe what Veeam Kasten does to stop a snapshot being deleted underneath you.

A VolumeSnapshot is a Kubernetes object that asks the storage layer for a point-in-time copy of a volume. The request is standard; the ability to honour it is not. That ability is a property of each individual CSI driver, which is why the useful question is never "can Kubernetes snapshot a volume" but "can this driver snapshot a volume".

Veeam Kasten can invoke volume snapshot operations through CSI, and three requirements have to be met for that to work: Kubernetes v1.14.0 or higher, the VolumeSnapshotDataSource feature enabled in the cluster, and a CSI driver that has Volume Snapshot support [Src: Kasten Docs 9.0.2 p.102]. Read the first two as inherited history: the releases this build supports start at Kubernetes 1.31 on a certified distribution, with 1.30 and 1.29 supported only as OpenShift [Src: Kasten Docs 9.0.2 p.862], and volume snapshots became a stable API long before any of them — so there is no feature gate left for you to switch on. Only the third requirement still has to be proved on your cluster. Using a CSI driver with VolumeSnapshot support is described as a requirement for building a good data protection solution with Veeam Kasten [Src: Kasten Docs 9.0.2 p.1090].

Prove it before you design around it

Whether a CSI provisioner supports VolumeSnapshots may be stated in the storage vendor's documentation, and it can also be validated with Veeam Kasten's own tooling rather than taken on trust [Src: Kasten Docs 9.0.2 p.1090].

The CSI pre-flight check is a real test

Run with a specified StorageClass, the primer tool — the pre-flight tool you install and run in Module 03 — runs in a Pod in the cluster and creates a sample application with a persistent volume, writes data to it, snapshots the volume, creates a new volume from that snapshot, and validates the data in the new volume [Src: Kasten Docs 9.0.2 p.102]. Module 03 covers both invocations: the basic run, and this one.

One annotation makes a class usable

For each CSI driver, a VolumeSnapshotClass has to carry the Veeam Kasten annotation before its snapshots can be used [Src: Kasten Docs 9.0.2 p.102]. You will apply it in Module 03; recognise it here.

yaml · the annotation that matters 
kind: VolumeSnapshotClass
metadata:
  annotations:
    k10.kasten.io/is-snapshot-class: "true"
  name: csi-hostpath-snapclass

The annotation and class name above are quoted from the Storage Integration reference [Src: Kasten Docs 9.0.2 p.102]. k10 appears in lowercase inside the annotation key k10.kasten.io/is-snapshot-class because that key is a verbatim technical string; the product name is Veeam Kasten.

Heads up — the most important sentence in this module

CSI snapshots are not durable. A snapshot has a namespaced VolumeSnapshot object and a non-namespaced VolumeSnapshotContent object, and with the default and recommended deletion policy, deleting the volume or the namespace containing it cleans up the namespaced object and cascades into deleting the VolumeSnapshotContent object and therefore the underlying storage snapshot [Src: Kasten Docs 9.0.2 p.102]. Setting deletionPolicy to Delete is not sufficient either, because some storage systems force snapshot deletion when the associated volume is deleted, and snapshots can also be force-deleted through the array's own management interface [Src: Kasten Docs 9.0.2 p.102]. Enabling backups together with volume snapshots is therefore required for a durable backup [Src: Kasten Docs 9.0.2 p.102].

The parallel you already trust

A storage snapshot is fast and cheap
True here too — it is the quickest route to a point-in-time copy, and the quickest route back.
A snapshot is not an independent copy
You already refuse to count array snapshots as your only backup. Keep refusing.
Retention is bounded by the array
Same instinct, same arithmetic: snapshot caps per volume limit what you can promise.

Where it is sharper here

01
One namespace deletion can take the snapshots with it.
In a virtual estate, deleting a VM does not commonly reach into the array and remove its snapshots. Here the cascade is documented behaviour [Src: Kasten Docs 9.0.2 p.102].
02
Veeam Kasten defends the copy it restores from.
It creates a clone of the original VolumeSnapshotClass with the deletion policy set to Retain, and when restoring a CSI VolumeSnapshot it creates an independent replica using that cloned class to avoid accidental deletion of the underlying content [Src: Kasten Docs 9.0.2 p.102].
03
Snapshot plus export is the shape of a real policy.
Snapshots give you speed on the cluster; an exported backup gives you the copy that survives the cluster. You need both, and that is a policy decision you will make in Module 05.
Helm · 07

Helm: charts, values, and releases

By the end of this section you'll be able to explain what a Helm chart is, what a release is, and what the install command you will run in Module 03 is doing — so that the installation reads as a familiar act rather than an incantation.

Helm is the package manager for Kubernetes applications. A chart is the package: a parameterised set of Kubernetes object definitions plus the default values for them. Values are the parameters you override at install time. A release is one named installation of a chart into a cluster — the thing that exists afterwards, that can be upgraded in place, and that can be rolled back or removed as a unit.

The closest thing in your current world is an installer package plus an answer file: the chart is the package, the values are the answers, and the release is the installed instance you later patch. Where the comparison breaks is that a release is not a set of files on a machine — it is a set of objects in the cluster's API, which is why an upgrade is a declaration change rather than a program that runs on a server.

Chart repository
A location Helm pulls charts from. Veeam Kasten's charts come from the Kasten Helm charts repository, which you add to Helm before installing [Src: Kasten Docs 9.0.2 p.4].
Chart version and product version
The chart version selects which Veeam Kasten version you install, so pinning it is how you control what lands in the cluster [Src: Kasten Docs 9.0.2 p.759].
Release name
The name you give the installation. Veeam Kasten's documented install names the release k10 [Src: Kasten Docs 9.0.2 p.4].
Target namespace
Where the release's objects are created. The Veeam Kasten install default is kasten-io [Src: Kasten Docs 9.0.2 p.15].

helm repo add kasten https://charts.kasten.io/

Did you know?

Helm is not the only route in. On Red Hat OpenShift there are two documented methods to install Veeam Kasten — a Helm-based installation and an Operator-based installation [Src: Kasten Docs 9.0.2 p.53]. Whichever you choose, the documentation encourages automating that deployment as part of the same tooling that builds the cluster, so that after a total cluster loss you can rebuild the platform and then recover applications and data with Veeam Kasten [Src: Kasten Docs 9.0.2 p.1090].

Pro tip

Two version checks save time later. The Helm 3 package manager has to be in place before installing, and its version should be compatible with the version of the Kubernetes cluster you are deploying into [Src: Kasten Docs 9.0.2 p.4]. Veeam Kasten's Helm chart can also be signature-verified with the published public key during installation [Src: Kasten Docs 9.0.2 p.4].

Veeam Kasten · 08

Where Veeam Kasten sits in all of this

By the end of this section you'll be able to describe Veeam Kasten's place in a cluster — which namespace it runs in, what shape it takes, how it finds applications without being told about them — and how that differs from the management server you are used to installing.

Veeam Kasten does not sit beside the cluster looking in. It runs inside the cluster, as a set of its own services in their own namespace. The install default for that namespace is kasten-io [Src: Kasten Docs 9.0.2 p.15], and after installing, the way you confirm the platform is healthy is to watch its Pods reach a running state [Src: Kasten Docs 9.0.2 p.15].

Those services are individually named — an aggregated API service, an authentication service, a catalog service and others appear in the Pod list [Src: Kasten Docs 9.0.2 p.15] — and Veeam Kasten's own tooling talks about validating a cluster before installation and debugging the platform's micro services afterwards [Src: Kasten Docs 9.0.2 p.866]. Read that as a design statement: this is not one monolithic server process, it is a set of cooperating in-cluster components.

shell · is the platform up? 
kubectl get pods --namespace kasten-io --watch

The documented validation step. All of the Pods should ultimately display a status of Running; it may take a couple of minutes for them to come up [Src: Kasten Docs 9.0.2 p.15].

It discovers instead of being told

Veeam Kasten's application object abstracts an application that has been automatically discovered on the cluster where Veeam Kasten is running, and captures its stateful and stateless resources together [Src: Kasten Docs 9.0.2 p.620]. There is no inventory to register and no agent to push.

It speaks the cluster's own language

Policies encode business rules and translate them into the actions Veeam Kasten applies to the applications it has discovered [Src: Kasten Docs 9.0.2 p.620]. Its own objects — policies, profiles, actions, restore points — live in the cluster API like any other Kubernetes resource.

It is hardened as an in-cluster tenant

Because it runs as Pods among other Pods, its security posture is a cluster concern: all Veeam Kasten Pods enable a read-only root filesystem security context by default, with writable paths backed by dedicated volume mounts [Src: Kasten Docs 9.0.2 p.1096]. On Red Hat OpenShift specifically, that posture has a name — Security Context Constraints: Veeam Kasten installs customized SecurityContextConstraints (SCC) to ensure that all workloads associated with it have just enough privileges to perform their respective tasks [Src: Kasten Docs 9.0.2 p.60].

Where the "management server" comparison breaks

A Veeam Backup & Replication server outlives the workloads it protects and holds its own configuration outside them. An in-cluster platform does not get that luxury: if the cluster is gone, Veeam Kasten is gone with it. That is why exported backups and a documented way to recover the platform itself matter here in a way they do not for a management server sitting on its own machine — and why the documentation is explicit that Veeam Kasten protects Kubernetes applications and cannot be used to deploy or restore the cluster's overall state [Src: Kasten Docs 9.0.2 p.1090]. Module 04 picks this up.
