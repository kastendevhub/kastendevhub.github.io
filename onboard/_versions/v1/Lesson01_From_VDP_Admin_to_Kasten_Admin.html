Orientation · 01

Why this is a different problem

Before any vocabulary, the shape of the problem has to change in your head. This section shows you what a Kubernetes application is made of, why "back up the disk" no longer describes the job, and what kind of product Veeam Kasten for Kubernetes is. After it, the concept map in the next section will read as obvious rather than arbitrary.

In your Veeam Data Platform world, the thing you protect has an edge you can point at. A virtual machine is a bounded object: a name in an inventory, a set of virtual disks, a configuration file. You select it, you protect it, and the boundary of what you captured is obvious.

Kubernetes gives you no such object. What a Veeam Kasten policy protects is defined as a collection of namespaced Kubernetes resources such as ConfigMaps and Secrets, the relevant non-namespaced resources the application uses such as StorageClasses, the Kubernetes workloads themselves — Deployments, StatefulSets, OpenShift DeploymentConfigs and standalone Pods — the deployment and release information available from Helm v3, and all of the persistent storage resources associated with those workloads, meaning the PersistentVolumeClaims and PersistentVolumes [Src: Kasten Docs 9.0.2 p.346]applicationIn Veeam Kasten, "application" is a defined technical term, not a loose word — it is the whole collection of Kubernetes objects listed here, captured together as one protected unit..

Read that list again as a backup admin. It is a dozen kinds of object, most of which hold no data at all — they hold the shape of the running system. Capture the volumes and miss the Secrets, and the restored application starts up and then fails to authenticate. Capture everything except the Helm release information, and the next upgrade has nothing to reconcile against. The data is the straightforward part; the assembly is the hard part.

What changes about the job

What is the unit of protection?
Not a machine. An application — a set of Kubernetes objects plus its volumes, protected together [Src: Kasten Docs 9.0.2 p.346].
Where does it live?
Inside a namespace on a cluster, alongside other applications. Namespace selection is how most policies choose what to protect [Src: Kasten Docs 9.0.2 p.347].
How do you find it?
You do not build an inventory by hand. Automatic application discovery is part of the platform [Src: Kasten Docs 9.0.2 p.2].
Does the cluster itself get protected?
Backing up control-plane components such as etcd and the system namespaces is not the recommended approach here; the focus is the applications [Src: Kasten Docs 9.0.2 p.1092].

Two ideas to carry forward

Everything else in this module rests on these. If only two sentences survive the week, make them these two.

01
You protect applications, not machines.
The unit is a namespace-scoped application with all its parts, and the parts that are not data matter as much as the parts that are.
02
A snapshot is not yet a backup.
In Veeam Kasten these are two separate policy actions with two separate lifetimes. Section 03 is entirely about this.

What Veeam Kasten for Kubernetes is

Veeam Kasten for Kubernetes is a data management platform purpose-built for Kubernetes, providing backup and restore, disaster recovery, and mobility for Kubernetes applications. Its approach is described as application-centric, it is policy-driven, and it exposes a native Kubernetes application programming interface (API) alongside a web-based user interface [Src: Kasten Docs 9.0.2 p.2].

Those three capabilities are the product's three principal use cases: backup and restore, disaster recovery, and application mobility [Src: Kasten Docs 9.0.2 p.2]. The first two you already own conceptually. The third — mobility — is the one with no clean Veeam Data Platform equivalent, and it is worth knowing why it exists here: because a Kubernetes application is described in portable manifests, an application captured on one cluster can be brought up on another, which makes cross-cluster movement a first-class feature rather than a recovery edge case.

Backup and restore

Protect an application and bring it back — into the same namespace, a different one, or a different cluster [Src: Kasten Docs 9.0.2 p.2].

Disaster recovery

Recover when the cluster or the site is gone, including recovering Veeam Kasten's own catalog [Src: Kasten Docs 9.0.2 p.1093].

Application mobility

Move an application and its data across clusters, and potentially across clouds, using a location profile [Src: Kasten Docs 9.0.2 p.315].

Remember

Your instincts about scheduling, retention, and proving a restore all transfer. What does not transfer is the assumption that the thing you protect has one obvious boundary. Build the habit of asking "which objects did that capture?" — it is the question this product is designed around.

The concept map · 02

Five concepts you already run

This is the backbone of the module and the thing to come back to. Five concepts you operate every day, each paired with its Veeam Kasten counterpart — and for each pair, the place where the analogy quietly stops being true. Work through the five yourself in the widget below; the full map is repeated as a table underneath so you can scan it later.

Try it · pick a concept you already know

Veeam Data Platform to Veeam Kasten, concept by concept

Select any of the five concepts below. Each opens the pair — what you run today on the left, its Veeam Kasten counterpart on the right — followed by the honest limit of the comparison. Arrow keys move between them.

What you run today — the backup job

A job names what to protect, when to run, where to put the result, and how long to keep it. It is the single object you open when someone asks why last night failed.

The counterpart — the policy

A policy defines a selection of Kubernetes resources plus one or more data management actions, configured to run on a periodic or event-driven basis. No policies exist after installation; you create every one [Src: Kasten Docs 9.0.2 p.307]. Actions can run at hourly, daily, weekly, monthly or yearly granularity, or on demand [Src: Kasten Docs 9.0.2 p.362].

Where the analogy breaks

A job's membership is a list you curated. A policy's membership is a selection — a namespace or a label expression — evaluated when the policy runs. Deploy a new application into a namespace a policy already selects and it is protected without anyone editing anything. That is a feature, and it is also how unreviewed workloads quietly land in your protected estate.

What you run today — the backup repository

A configured storage target that jobs write to. You add it once, jobs point at it, and it holds the backup files.

The counterpart — the location profile

For actions that outlive any one cluster, Veeam Kasten needs configured access to external object storage or external NFS or SMB file storage, and that is what a location profile provides. Location profiles are used to create backups from snapshots, to move applications and their data across clusters and potentially across clouds, and to import those backups into another cluster [Src: Kasten Docs 9.0.2 p.315].

Where the analogy breaks

Resist the habit of treating the target as a folder you can also poke at. The exported data is organised into storage repositories controlled and maintained by the Veeam Kasten instance, and using, connecting to, modifying, copying, or otherwise accessing one of those repositories independently is unsupported and might cause data corruption or loss to some or all of the restore points [Src: Kasten Docs 9.0.2 p.352]. Read-only curiosity is not a safe habit here.

What you run today — snapshot versus backup

You already hold the distinction: a storage or hypervisor snapshot is fast and local and dependent on the production system; a backup is a separate copy you can survive a storage failure with. You know which one you would want at 3am.

The counterpart — snapshot versus export

Snapshots are the basis of persistent data capture in Veeam Kasten [Src: Kasten Docs 9.0.2 p.349]. A backup is produced by an export, which converts application and volume snapshots into backups by transforming them into an infrastructure-independent format and storing them in a target location [Src: Kasten Docs 9.0.2 p.351].

Where the analogy breaks

This is the row where your instincts help you the most and your muscle memory helps you the least. The distinction is familiar, but in Veeam Kasten the export is an explicit, separately configured, separately scheduled, separately retained action that you have to turn on. A policy that snapshots nightly and exports nothing runs green forever and leaves you with no durable copy. Section 03 walks the whole chain.

What you run today — application-aware processing

You tick a box and the product quiesces the database before the snapshot, then releases it. The mechanism is built in, and for the workloads it covers you rarely think about it.

The counterpart — Kanister blueprints and action hooks

Application-consistent backups can be enabled where a data service needs quiescing before a volume snapshot: a quiescing function defined in the application blueprintblueprintA Kanister blueprint is the Kubernetes object that holds the application-specific actions Veeam Kasten calls at defined points in a backup or restore. is invoked first, then the volume snapshot is taken, and the application is unquiesced as soon as the storage system reports that the point-in-time copy has started rather than waiting for the whole snapshot [Src: Kasten Docs 9.0.2 p.923]. Blueprints can also run as action hooks on a policy [Src: Kasten Docs 9.0.2 p.890].

Where the analogy breaks

Application-aware processing is a checkbox. This is an object you deploy and bind. A blueprint is assigned to a workload either by creating a BlueprintBinding or by adding the kanister.kasten.io/blueprint annotation, Veeam Kasten looks for blueprints in its own namespace only, and it calls only actions with reserved names such as backupPrehook and backupPosthook — an action with a name outside that set is silently ignored unless it is configured as a policy action hook [Src: Kasten Docs 9.0.2 p.890]. "Silently ignored" is the phrase to underline.

What you run today — proxies and agents

Data movement is done by roles you deploy, size, and place: proxies near the data, agents on the guest. You scale them by adding more, and you troubleshoot a slow job by looking at them.

The counterpart — in-cluster services

Veeam Kasten runs as a set of services inside the cluster, in its own namespace — the install default is kasten-io [Src: Kasten Docs 9.0.2 p.15] — as Pods you can list. The names show the division of labour: catalog-svc, executor-svc, crypto-svc, controllermanager-svc, dashboardbff-svc, aggregatedapis-svc, auth-svc, frontend-svc, jobs-svc, kanister-svc and state-svc [Src: Kasten Docs 9.0.2 p.49, p.50].

Where the analogy breaks

You do not place these. There is no proxy to put on the right subnet and no agent to push to a guest — the platform you are protecting is also the platform that runs the protection, and it decides where those Pods land. Data-moving Pods are created for the work and cleaned up afterwards rather than sitting idle: export Pods are removed by garbage collection after a configured grace period [Src: Kasten Docs 9.0.2 p.1097]. Your sizing conversation moves from "how many proxies" to "what resources does this cluster have spare".

Takeaway: four of these five map cleanly enough to trust. The snapshot-versus-export row is the one that costs people real data, because it feels the most familiar.

Data capture · 03

A snapshot is not a backup until you export it

This is the single most expensive misunderstanding available to a Veeam Data Platform administrator arriving at Veeam Kasten, so it gets its own section. Work through the three stages below and you will be able to look at any policy and answer the only question that matters: if the storage system went away tonight, what would still exist tomorrow?

Start with what a snapshot is good at, because it is genuinely good. Snapshots are the basis of persistent data capture in Veeam Kasten, and on most storage systems their performance impact on the primary workload is low, they need no downtime, they restore quickly, and they capture data incrementally [Src: Kasten Docs 9.0.2 p.349]. That is a strong set of properties, and it is why the snapshot action is the one every policy starts from.

Now the limits, stated plainly in the documentation. Storage snapshots suffer from constraints such as relatively low limits on the maximum number of snapshots per volume or per storage array. More importantly, snapshots are not always durable: a catastrophic storage system failure will destroy your snapshots along with your primary data, and on a number of storage systems a snapshot's lifecycle is tied to its source volume, so deleting the volume may garbage-collect every related snapshot at the same time [Src: Kasten Docs 9.0.2 p.349]. The documented guidance that follows is direct: create durable backups by exporting the data [Src: Kasten Docs 9.0.2 p.349].

One nuance worth carrying, because it stops this becoming dogma. A number of public cloud providers store snapshots in object storage and retain them independently of the primary volume's lifecycle — though this is not true of all public clouds, and enabling exports in a public cloud may still be worthwhile for safety [Src: Kasten Docs 9.0.2 p.350]. "Snapshots are never durable" is too strong; "you do not get to assume they are" is right.

Stage 01 — Snapshot. Every policy that protects an application starts with the snapshot action, with an optional export action after it to produce a durable backup [Src: Kasten Docs 9.0.2 p.348]. STAGE 02
Export
The snapshot becomes a portable backup.
Stage 02 — Export. To convert snapshots into backups you select Enable Backups via Snapshot Exports during policy creation, and the same settings are available when manually exporting a restore point [Src: Kasten Docs 9.0.2 p.352]. The export transforms the application and volume snapshots into an infrastructure-independent format and stores them in a target location [Src: Kasten Docs 9.0.2 p.351]. The backup it produces consists of the application's metadata plus the snapshot data for its volumes, and the metadata destination is an Object Storage Location, an NFS or SMB File Storage Location, or a Veeam Repository Location, named in the Export Location Profile field [Src: Kasten Docs 9.0.2 p.352]. Retention is configured separately: by default backup retention matches snapshot retention, but the two can be set independently [Src: Kasten Docs 9.0.2 p.364].

STAGE 03
Restore point
Two kinds of restore point, and you pick.
Stage 03 — Restore point. A restore point is a grouped collection of the data artifacts belonging to an application, and the restore view distinguishes snapshots from backups as well as manual restore points from policy-generated ones. When both a snapshot and a backup exist for the same data, a layered box indicates it, and selecting that layered restore point lets you choose between the local snapshot and the exported backup [Src: Kasten Docs 9.0.2 p.395]. This is the screen that tells you the truth about a policy — if an application only ever shows one kind, you know which action is not running.
The failure mode, spelled out A policy with the snapshot action alone will report success indefinitely. Its compliance is fine, its history is green, and its restore points are real — until the storage system that holds them fails, at which point the snapshots go with the primary data [Src: Kasten Docs 9.0.2 p.349]. Nothing in that policy's own status will ever tell you this. The check is structural, not operational: does this policy export, and to where?
Did you know?

The separation is not only a safety mechanism — it is a cost lever, and the documented pattern will look familiar to anyone who has tuned local versus offloaded retention. The guidance is to reduce local retention, which can be more expensive, and increase remote retention, which is more cost-effective; you can run shorter retention on snapshots and extended periods on exports, and you can even split the work across two policies so one snapshots without exporting and the other snapshots and exports [Src: Kasten Docs 9.0.2 p.1092].

In the cluster · 04

What gets deployed, and which edition

Two practical questions a Veeam Data Platform administrator asks early: what does this put on the cluster, and what am I licensed for? Neither answer is complicated, and both change how you talk about Veeam Kasten with the platform team who owns the cluster.

It is a workload on the cluster it protects

Veeam Kasten is deployed into its own namespace, kasten-io by convention, and runs as a set of Pods there. After an install you confirm it the same way you would confirm any Kubernetes workload — by listing the Pods in that namespace and waiting for all of them to reach Running [Src: Kasten Docs 9.0.2 p.15].

shell 
kubectl get pods --namespace kasten-io

That one command replaces a surprising amount of your old troubleshooting surface. There is no proxy server to log into, no agent version to reconcile, and no separate management host: the services listed in the concept map are all Pods in that namespace, and Module 04 covers watching them as the workload they are. Module 03 covers getting them there, which is a Helm install of the kasten/k10 chart into that namespace [Src: Kasten Docs 9.0.2 p.4].

Supplementary · optional Why the product's technical strings still say k10

The product is Veeam Kasten for Kubernetes, and that is what you call it. You will nonetheless meet the string k10 constantly and it is not a mistake — it is the chart and release name in the documented install command [Src: Kasten Docs 9.0.2 p.4]:

helm install k10 kasten/k10 --namespace=kasten-io

Treat those as identifiers, the way you treat a service name in a config file. When you type a command, type what the documentation types. When you write or speak about the product, use its name.

Two editions, one install

Veeam Kasten is available in two editions [Src: Kasten Docs 9.0.2 p.2]. The detail that matters operationally is that both editions use the same container images and follow an identical install process [Src: Kasten Docs 9.0.2 p.3] — so the edition question is a licensing conversation, not an architecture one.

Starter — also called Veeam Kasten Free

What does it cost?
It is the default edition and is provided at no charge [Src: Kasten Docs 9.0.2 p.2].
What is it intended for?
Evaluation, or use in small non-production clusters [Src: Kasten Docs 9.0.2 p.2].
What is missing from it?
Functionally it is the same as Enterprise, but limited from a support and scale perspective [Src: Kasten Docs 9.0.2 p.2].

Enterprise

How do you get it?
Customers choosing to upgrade obtain a license key from Kasten, or install from cloud marketplaces [Src: Kasten Docs 9.0.2 p.3].
Is it a different build?
No — the same container images and the same install process as Starter [Src: Kasten Docs 9.0.2 p.3].
Where is the feature comparison?
The documentation points at the Kasten product page for a comparison of the editions rather than listing one [Src: Kasten Docs 9.0.2 p.3].
Heads up

"Functionally the same" is a phrase to read carefully rather than gratefully. It means a proof of concept on the Starter edition demonstrates real behaviour, which is a genuine advantage. It does not mean a Starter deployment is a supported production deployment — the limits are on support and scale, and both of those are exactly what you need when a restore matters [Src: Kasten Docs 9.0.2 p.2].

Where your repositories fit · 05

Exporting to a Veeam Backup & Replication repository

Here is where your existing estate re-enters the picture. A Veeam Backup & Replication repository can be the destination a Veeam Kasten policy exports to, which means Kubernetes data can land in storage you already own, monitor, and pay for. This section covers what that gives you and the constraints that come attached — including one that has caught experienced administrators.

A Veeam Repository can serve as the destination for both the application metadata and the persistent volume snapshot data, for any cluster where a Veeam Backup & Replication repository is available and the storage provisioner for the persistent volumes supports block mode export [Src: Kasten Docs 9.0.2 p.127]. In location-profile terms it is one more type of target alongside object storage and NFS or SMB file storage [Src: Kasten Docs 9.0.2 p.352].

What arrives on the other side will look reassuringly familiar. A Veeam Backup & Replication backup job is created on the server for each Veeam Kasten policy, with a Veeam Kasten catalog identifier appended to the job name so that clusters backing up to the same server stay distinct, and each protected application namespace produces a single, separate restore point object. Following export, each backup is converted to a synthetic full backup [Src: Kasten Docs 9.0.2 p.129].

The constraints to know before you promise it

Constraints on exporting from Veeam Kasten to a Veeam Backup & Replication repository
ConstraintWhat it means for you
Block mode export is mandatory Exporting to a Veeam Repository requires the block mode export mechanism for all volume snapshots the policy creates, and selecting a Veeam Repository as the Export Location Profile enables block mode export automatically [Src: Kasten Docs 9.0.2 p.128]. The storage provisioner has to be capable of block mode exports [Src: Kasten Docs 9.0.2 p.129].
Not every repository type qualifies Export to Veeam Backup & Replication direct object storage repository types is not supported [Src: Kasten Docs 9.0.2 p.128].
One backup server per instance Each Veeam Kasten instance may export to a single, unique Veeam Backup & Replication backup server. Multiple location profiles may point at separate repositories exposed by that same server, and multiple Veeam Kasten instances may integrate with the same server [Src: Kasten Docs 9.0.2 p.129].
Copies made downstream are not restore sources Copies of the backup data produced inside Veeam Backup & Replication — by exporting to a scale-out backup repository (SOBR), by backup copy jobs, or by backup to tape jobs — cannot be directly restored in Veeam Kasten [Src: Kasten Docs 9.0.2 p.129].
One object per export, not per volume All exported volume data is uploaded by a single datamover Pod and stored as a single object in the repository for each export, independent of how many persistent volumes the policy protects [Src: Kasten Docs 9.0.2 p.129].
The one that catches people Read the fourth row again, because it inverts a reflex. Your instinct with any new data source is to get it into the wider protection chain — copy it out, tier it, send it to tape. Those copies remain valid Veeam Backup & Replication restore points and you may well still want them, but Veeam Kasten cannot restore an application directly from them [Src: Kasten Docs 9.0.2 p.129]. Decide deliberately which copy is the one your Kubernetes recovery plan depends on, and write it down.
For a customer conversation

The value here is not a feature list, it is an operating model. A customer adopting Kubernetes does not have to stand up a parallel backup estate with its own storage, its own retention argument, and its own audit story — the Kubernetes applications can export into the repository their virtual estate already uses, and the constraints above are the honest fine print you should raise yourself rather than have discovered later.

Remember

Two more things worth holding from this section. A manual export that is not associated with a policy produces a standalone K10ManualBackup backup job containing the application namespace, saved as a full, independent VeeamZIP backup [Src: Kasten Docs 9.0.2 p.129]. And an exported restore point can be imported and restored on another supported cluster, provided the target cluster is configured with the same Veeam Repository location profile used for the volume data [Src: Kasten Docs 9.0.2 p.129] — which is application mobility using storage you already run.
