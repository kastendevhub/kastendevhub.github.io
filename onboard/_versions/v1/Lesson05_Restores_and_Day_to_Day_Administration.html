Policies · 01

Building a policy: schedule, snapshot, export, retention

This is the section where your Veeam Data Platform muscle memory earns its keep. By the end of it you can build a Veeam Kasten for Kubernetes policy from a blank form — pick what it protects, how often it runs, whether it exports, and how long each tier of restore point survives — and you will know which of your backup-job instincts to keep and which one to put down.

Protecting an application with Veeam Kasten, which is accomplished by creating a policy, rests on three concepts: snapshots and exports (one or both of the data-capture mechanisms), scheduling (capture frequency plus snapshot and backup retention objectives), and selection (which applications the policy protects, with resource filtering when finer control is needed) [Src: Kasten Docs 9.0.2 p.346]. If you read "job settings, schedule, and job scope" while you read that sentence, your mental model is close enough to start.

What a policy protects is an application, and Veeam Kasten defines that term precisely: a collection of namespaced Kubernetes resources, the relevant non-namespaced resources the application uses, the Kubernetes workloads, deployment and release information available from Helm v3, and all of the persistent storage resources associated with those workloads [Src: Kasten Docs 9.0.2 p.346]. A new policy can be created from the Policies page or from the Applications page, and starting from the Applications page pre-populates the policy name and the namespace selection [Src: Kasten Docs 9.0.2 p.347].

Snapshot, export, or both

All policies centre on the execution of actions, and for protecting applications you start with the snapshot action and add an optional export action to produce a durable backup [Src: Kasten Docs 9.0.2 p.348]. Those are not two names for one thing. The difference is the single most important idea in this module, because it decides where a restore can come from.

Snapshot

Where does it live?
On the storage system that holds the volumes, alongside the primary data [Src: Kasten Docs 9.0.2 p.349].
What is it good at?
Low performance impact on the primary workload, no downtime, fast restore times, and incremental data capture [Src: Kasten Docs 9.0.2 p.349].
Where does it fall down?
Storage systems set relatively low limits on snapshots per volume or per array, and snapshots are not always durable: catastrophic storage failure destroys them along with the primary data, and in a number of systems a snapshot's lifecycle is tied to the source volume, so deleting the volume can garbage-collect the snapshots with it [Src: Kasten Docs 9.0.2 p.349].

Export (the backup)

Where does it live?
In a target location outside the cluster's primary storage. The metadata destination is an Object Storage Location, an NFS/SMB File Storage Location, or a Veeam Repository Location, named in the Export Location Profile field [Src: Kasten Docs 9.0.2 p.352].
What is it good at?
Export operations convert application and volume snapshots into backups by transforming them into an infrastructure-independent format and storing them in that target location [Src: Kasten Docs 9.0.2 p.351] — which is what makes them durable, portable, and restorable on a different cluster.
How do I turn it on?
Select Enable Backups via Snapshot Exports during policy creation; the destination and the control over exporting snapshot data versus a reference appear there too [Src: Kasten Docs 9.0.2 p.352].
Remember

A snapshot-only policy is a policy with no durable copy. Because of the limitations of snapshots, setting up backups of your application stack is advisable, and durable backups are created by exporting data [Src: Kasten Docs 9.0.2 p.349]. Treat "snapshot plus export" as the default shape of a production policy and make yourself justify any policy that stops at the snapshot.

Heads up

Exported data is organized into storage repositories that are exclusively controlled and maintained by the Veeam Kasten instance. Independently using, interacting with, connecting to, modifying, copying, upgrading, or in any way accessing or manipulating a Veeam Kasten storage repository is unsupported and can cause data corruption or loss to some or all of the restore points [Src: Kasten Docs 9.0.2 p.352]. Whatever housekeeping habits you have for a backup repository you can browse, leave them at the door for this one.

Scheduling has four moving parts

Scheduling in Veeam Kasten breaks into four components: how frequently the primary snapshot action runs, how often snapshots are exported into backups, the retention schedule of snapshots and backups, and when the primary snapshot action runs [Src: Kasten Docs 9.0.2 p.362]. Work through them in that order and the form stops feeling crowded.

Try it · the order to fill the form in

Four decisions, in the order the form wants them

Click a step to open it. One opens at a time.

  1. 1

    Actions can be set to execute at an hourly, daily, weekly, monthly, or yearly granularity, or on demand. By default, actions set to hourly execute at the top of the hour and other actions execute at midnight UTC [Src: Kasten Docs 9.0.2 p.362]. You can also select the time at which scheduled actions execute, and sub-frequencies that run multiple actions per frequency [Src: Kasten Docs 9.0.2 p.362].

    Sub-hourly actions are useful when what you are protecting is chiefly Kubernetes objects or small data sets; care should be taken with more general-purpose workloads because of the risk of stressing the underlying storage infrastructure or running into storage API rate limits [Src: Kasten Docs 9.0.2 p.362]. Sub-frequencies also interact with retention: retaining 24 hourly snapshots at 15-minute intervals would only retain six hours of snapshots [Src: Kasten Docs 9.0.2 p.362]. That single sentence has caught out more people than any other line on this page.

  2. 2

    Backups performed via exports are, by default, set up to export every snapshot into a backup, and it is also possible to select a subset of snapshots for exports — for example, converting only every daily snapshot into a backup [Src: Kasten Docs 9.0.2 p.362]. That subset choice is the lever you pull when hourly snapshots are cheap on the array and expensive in the object store.

    One constraint to design around before you save: to maintain backup recovery points, once the policy is saved the export location profile can only be changed to a compatible location profile. The interface enforces compatibility when you edit a policy, but no compatibility enforcement is performed when editing the policy custom resource directly [Src: Kasten Docs 9.0.2 p.363].

  3. 3

    Veeam Kasten can use a grandfather-father-son (GFS) retention scheme for cost and compliance reasons. Under that backup rotation scheme, hourly snapshots and backups rotate on an hourly basis with one graduating to daily every day, and so on; you set the number of hourly, daily, weekly, monthly, and yearly copies to retain, and Veeam Kasten handles both cleanup at every retention tier and graduation to the next one. For on-demand policies it is not possible to set a retention schedule [Src: Kasten Docs 9.0.2 p.364].

    Backup retention schedules default to the same values as snapshot retention schedules, and can be set to independent schedules if needed — which lets you keep a limited number of snapshots for fast recovery from accidental outages while storing a larger number of backups for long-term recovery needs [Src: Kasten Docs 9.0.2 p.364].

    Two behaviours worth knowing before they surprise you. The retention schedule for a policy does not apply to snapshots and backups produced by manual policy runs; any artifacts created by a manual run need to be cleaned up manually [Src: Kasten Docs 9.0.2 p.364]. And restore points created by failed policy runs do not count towards retiring older restore points — they are retained until there are enough newer restore points from successful runs to satisfy the retention counts, which can leave you with more restore points than you expected while a policy is failing [Src: Kasten Docs 9.0.2 p.364].

  4. 4

    The Advanced Options settings let you pick how many times and when actions execute within the interval of the frequency — for a daily frequency, which hour or hours within each day and which minute within each hour [Src: Kasten Docs 9.0.2 p.366]. By default hourly retention counts apply to the hourly action at the top of the hour, daily counts to the action at midnight, weekly counts to midnight Sunday, monthly counts to midnight on the first of each month, and yearly counts to midnight on 1 January, all in UTC [Src: Kasten Docs 9.0.2 p.366]. Advanced Options lets you display and enter times in either local time or UTC; all times are converted to UTC, and Veeam Kasten policy schedules do not change for daylight savings time [Src: Kasten Docs 9.0.2 p.366].

    The Backup Window settings let you select a time interval within which the policy will run. The policy is scheduled to run once at the Backup Window start time, and if the selected interval is too short the policy run will not finish and will be canceled [Src: Kasten Docs 9.0.2 p.367]. If the policy has an hourly frequency and the window exceeds one hour, the policy is also scheduled to run every 60 minutes thereafter within the window [Src: Kasten Docs 9.0.2 p.367].

    With staggering enabled, Veeam Kasten automatically finds an optimal start time and runs the policy within the selected interval, which lets it stagger runs of multiple policies and reduce peak load on the overall system [Src: Kasten Docs 9.0.2 p.367].

The policy is an object on the cluster

One habit to add rather than transfer: everything the policy form produces is a Kubernetes custom resource, and you can read or edit it directly. A Policy represents a collection of data management actions configured to occur on a periodic or event-driven basis, encoding business rules and translating them into the specific actions Veeam Kasten applies to the applications it has discovered [Src: Kasten Docs 9.0.2 p.620]. Policies can also be edited directly by modifying the custom resource YAML through the dashboard or the command line [Src: Kasten Docs 9.0.2 p.388]. The excerpt below is the top of a documented daily policy that retains seven daily and four weekly snapshots [Src: Kasten Docs 9.0.2 p.642].

yaml · Policy custom resource 
apiVersion: config.kio.kasten.io/v1alpha1
kind: Policy
metadata:
  name: multi-cloud-export-policy
  namespace: kasten-io
spec:
  comment: Multi-region backup policy with exports to S3 primary and secondary regions
  frequency: '@daily'
  retention:
    daily: 7
    weekly: 4

Reading a policy this way pays off the first time someone asks why a run did not happen: the schedule and the retention counts are right there, in one object, with no form to navigate. It also explains the compatibility warning above — the interface guards you when you edit through it, and does not when you edit the resource directly [Src: Kasten Docs 9.0.2 p.363].

Reading the status your policy produces

After you create a policy and return to the dashboard, the application status updates from Unmanaged to Non-Compliant, which indicates that a policy exists but has not successfully run within the specified frequency; the status changes to Compliant on successful completion of a scheduled or manual run [Src: Kasten Docs 9.0.2 p.384]. Those labels are defined on the dashboard as: Unmanaged, meaning no protection policies cover the object; Non-compliant, meaning a policy applies but its actions are failing or have not been invoked yet; Compliant, meaning policies apply and their service-level objectives are being respected; and Removed, meaning objects that are removed [Src: Kasten Docs 9.0.2 p.301]. Scrolling down the page gives visibility into individual action activity, and clicking an in-progress or completed job gives the detail [Src: Kasten Docs 9.0.2 p.385].

Did you know?

A policy that has gone invalid will not run, and that can produce a compliance breach; revalidation exists for exactly that case, through the Revalidate menu option on the Policies page [Src: Kasten Docs 9.0.2 p.387]. Worth knowing the option is there before you go looking for a deeper problem.

Restores · 02

Getting data back: which path, and how far in

This is the section you will come back to under pressure, so it is built as a decision rather than a tour. By the end of it you can pick between a local snapshot, an exported restore point, and an imported one; choose in-place, new-namespace, volume-level, or file-level granularity; and say in advance what a restore will do to a resource that already exists in the target namespace.

Once applications have been protected via a policy or a manual action, it is possible to restore them in place or clone them into a different namespace [Src: Kasten Docs 9.0.2 p.392]. Restoring an existing application is done from the Applications page by clicking the Restore option in the dropdown; alternatively, the Restore Points page can be used to find a specific restore point and initiate the restore from it [Src: Kasten Docs 9.0.2 p.393].

Set expectations on duration before you promise anything to an application owner. A restore can take a few minutes, depending on the amount of data captured by the restore point, and the time is dominated by how long it takes to rehydrate captured data followed by recreating the application containers, so it tracks the speed of the underlying storage infrastructure [Src: Kasten Docs 9.0.2 p.392]. Retries are built in: to speed up the restore and account for failures during the first or second attempt, up to a maximum of three attempts, all successfully restored volumes are retained for the next attempt and only partially restored volumes are recreated [Src: Kasten Docs 9.0.2 p.392].

Snapshot or exported backup — the interface tells you which you have

When you pick a restore point you are picking a restore pointrestore pointCreated as a result of a backup or import action, it represents a version-in-time of an application that Veeam Kasten has captured and that can be restored using a restore action [Src: Kasten Docs 9.0.2 p.620]., a grouped collection of data artifacts belonging to the application, and the view distinguishes manually generated restore points from automated policy-generated ones [Src: Kasten Docs 9.0.2 p.395]. It also distinguishes between snapshots and backups: when both are present a layered box indicates that more than one kind of restore point exists for the same data, and clicking that layered restore point presents the option to select between the local snapshot and the exported backup [Src: Kasten Docs 9.0.2 p.395]. Selecting a restore point brings up a side panel with more detail on it, so you can preview before initiating the restore [Src: Kasten Docs 9.0.2 p.396].

Heads up

The word "export" in the interface does not mean you need an import policy to use the result. While the interface uses the Export term for backups, no import policy is needed to restore from a backup; import policies are only needed when you want to restore the application into a different cluster [Src: Kasten Docs 9.0.2 p.395]. Restoring on the same cluster from an exported backup is the ordinary restore workflow.

Choose the right restore path

Five situations. For each one, pick the path you would take and read the reasoning that comes back. Two questions decide most real cases: is the local snapshot still trustworthy, and does the data need to land back on top of the running application?

A bad configuration change went out half an hour ago
Context: the cluster, its nodes, and the storage behind the volumes are all healthy.
You need the application back at the state it held before the change.

The local snapshot is the fast path while the storage under it is intact — snapshots support fast restore times and implement incremental data capture, with low performance impact on the primary workload [Src: Kasten Docs 9.0.2 p.349]. The exported backup would also work, and would cost you a rehydration you did not need to pay for.

The storage system holding the volumes has failed
Context: the cluster is fine, the array is not, and the volume snapshots went with it.
You need a copy that did not live on the failed system.

This is the scenario the export tier exists for. Snapshots are not always durable: catastrophic storage system failure destroys your snapshots along with your primary data, and in a number of storage systems a snapshot's lifecycle is tied to the source volume [Src: Kasten Docs 9.0.2 p.349]. The exported backup sits in an infrastructure-independent format in a separate target location [Src: Kasten Docs 9.0.2 p.351], which is why it survives.

Developers want last night's data to reproduce a bug
Context: production must keep serving traffic while they work.
You need a copy of the application stack that nobody is depending on.

By default Veeam Kasten restores applications into the original namespace the restore point was created from, but the target namespace can be changed and new namespaces can be created at that point; debugging, test and development, and cloning are documented uses of exactly that [Src: Kasten Docs 9.0.2 p.416]. Restoring in place would recreate the entire application stack into the selected namespace [Src: Kasten Docs 9.0.2 p.396] — an outage you did not need to take.

Someone deleted three files inside one large volume
Context: the rest of the application is healthy and busy.
You need three files, not a volume and not an application.

Veeam Kasten provides the FileRecoverySession custom resource to request network access to files from exported restore points without requiring a full restore of volume data [Src: Kasten Docs 9.0.2 p.419]. A Volume-Clones restore is the next-best answer and a good one: it restores individual volumes into the existing application namespace without disrupting its operation or workloads [Src: Kasten Docs 9.0.2 p.408], though you then mount and copy by hand. A full application restore is the sledgehammer.

The cluster is gone; a replacement is running in another region
Context: the export location profile and its data are intact.
You need the applications running on a cluster that has never seen them.

Import policies are supported for importing applications into a cluster that is different from where the application was captured [Src: Kasten Docs 9.0.2 p.460], and this is the path section 03 walks. One dependency decided months earlier: if migration across clusters in different clouds or between on-premises and public cloud is needed, the Export Snapshot Data option must be enabled on the source policy, because without it the application data is not exported and the subsequent import will fail [Src: Kasten Docs 9.0.2 p.455].

Every path above is reachable from the same restore workflow. What changes is the restore point you select and the options you set on the way through.

Two questions settle almost every case. Is the local snapshot still trustworthy? If the storage under it is intact, take the snapshot; if the storage failed, take the exported backup, because that is the copy in an infrastructure-independent format outside the cluster's primary storage [Src: Kasten Docs 9.0.2 p.351]. Then: does the data have to land on top of the running application? If not, restore into a different namespace instead, which is a supported target choice at restore time [Src: Kasten Docs 9.0.2 p.416]. Only when the source cluster itself is unavailable does the answer become an import policy, because import policies are for clusters other than the one that captured the application [Src: Kasten Docs 9.0.2 p.460].

What a restore does to what is already there

This is where "restore an application" stops behaving like "restore a virtual machine". When you click Restore, the system recreates the entire application stack into the selected namespace, including the data associated with the original application and the versioned container images [Src: Kasten Docs 9.0.2 p.396]. A resource that does not currently exist in the namespace is always restored; the treatment of namespaced resources that do already exist depends on the type of resource and the overwriteExisting flag [Src: Kasten Docs 9.0.2 p.396]. Read the table before your first production restore, not after it.

Three levels of granularity

By default a restore brings back all artifacts and data captured during the backup process. Where only a subset is required, the restore workflow supports artifact filtering for full control over what artifacts and data to restore, a data-only restore for a running application, and a volume-clones restore for restoring volumes only [Src: Kasten Docs 9.0.2 p.406].

You can selectively bring back restore point artifacts, including volume snapshots, which is useful for scenarios such as a single persistent volume claim restore or rolling back configuration updates; by default all artifacts are selected for restore [Src: Kasten Docs 9.0.2 p.406]. One trap to design around: to preserve owner references, both the resource and its owners must be included by the filters [Src: Kasten Docs 9.0.2 p.407].

A data-only restore looks like selecting all volume snapshots and no Kubernetes specifications, but it carries safety guardrails: the Kubernetes workloads captured in the restore point must exist in the namespace the application is being restored into, the running workloads must have the same number of replicas as captured in the restore point, and they must have the same volumes as were gathered — the same number of volumes, with the same names [Src: Kasten Docs 9.0.2 p.407]. Those checks exist because data-only restore is frequently used to bring older versions of data into a newer version of application code [Src: Kasten Docs 9.0.2 p.407].

Know what it does to the volumes underneath: a data-only restore follows a delete-and-restore-from-backup approach for the persistent volume claims, to maintain data integrity [Src: Kasten Docs 9.0.2 p.408]. This is not an in-place merge.

Volume-clones restore enables restoring individual volumes into the existing application namespace without disrupting its operation or workloads, which suits recovering specific files from a backup when restoring the volume to an alternative namespace is not permitted or desirable [Src: Kasten Docs 9.0.2 p.408]. The workloads captured in the restore point can exist in the target namespace without being affected [Src: Kasten Docs 9.0.2 p.408].

Three consequences to plan for. The restored claims follow a naming convention that appends the restore point's creation timestamp to the original claim name to denote that they are clones; the restore does not automatically mount volumes to any pods, so mounting them is your responsibility; and each cloned claim carries the label k10.kasten.io/cloned: "true", which can be used as a policy exclusion to prevent the cloned volumes from being included in a backup policy by accident [Src: Kasten Docs 9.0.2 p.409]. Once the cloned claims have served their purpose, removing them from the namespace is recommended, which keeps them out of future backups and prevents unnecessary data duplication [Src: Kasten Docs 9.0.2 p.409].

Supplementary · optional Going one level finer: recovering individual files

Veeam Kasten provides the FileRecoverySession custom resource to request network access to files from exported restore points without requiring a full restore of volume data, and the k10tools frs sub-command provides a command-line interface for the related operations, including a built-in file transfer client [Src: Kasten Docs 9.0.2 p.419]. File data is made available through the OpenSSH implementation of the Secure File Transport Protocol, via a dedicated service created for each custom resource instance, and the service only permits access by the principal whose public key was provided in the request [Src: Kasten Docs 9.0.2 p.420].

Two constraints shape whether this is available to you at all. Only exported restore points should be specified in the request [Src: Kasten Docs 9.0.2 p.420] — a local snapshot is not enough. And the files must sit in a volume that was exported in filesystem mode, or exported in block mode where the volume is unpartitioned and contains an ext4, xfs or ntfs filesystem, or has a GPT or MBR partition table with one or more filesystem partitions containing those filesystems, with the guest filesystem not encrypted [Src: Kasten Docs 9.0.2 p.419].

Exported restore points can be distinguished from local restore points with a label query [Src: Kasten Docs 9.0.2 p.420]:

shell · list exported restore points 
kubectl get restorepoints -n app2 -l k10.kasten.io/exportProfile

Sessions are not permanent. A session in the Ready state has a limited lifetime, and at the time given in its expiry field its state changes to Failed; the session is terminated by deleting the custom resource, which releases the accumulated system and Kubernetes resources [Src: Kasten Docs 9.0.2 p.421]. The default session expiry is 30 minutes, set by the frs.sessionExpiryTimeInMinutes Helm parameter [Src: Kasten Docs 9.0.2 p.419].

Restoring many applications at once

To restore several applications together you select them in the table and use the Restore selected option in the Options menu; you then select restore points for each application, with the most recent available restore point preselected by default, and applications can be excluded from the operation if no valid restore point satisfies the need [Src: Kasten Docs 9.0.2 p.401]. The workflow then differs from the single-application one in useful ways: you can add a prefix or suffix to the target namespace or filter resources in the Restore Configuration step, a Summary screen gives an overview of the operations and the options enabled throughout, and cluster-scoped resources can be restored along with the selected applications [Src: Kasten Docs 9.0.2 p.402].

Pro tip

One control in the multiple-application workflow is built for the worst day. You can specify a date range — during a ransomware attack, for example — in order to choose the latest restore point containing unencrypted data even when more recent restore points exist that may contain corrupted data; when a date range is selected, the most recent restore point within that range is automatically selected for each application [Src: Kasten Docs 9.0.2 p.401]. Practise using it before you need it.

Applications, and the virtual machines among them

One place where the application-shaped model meets your existing world: Veeam Kasten also protects virtual machines running on KubeVirt-based platforms such as Red Hat OpenShift Virtualization or SUSE Virtualization, through virtual-machine-based policies that allow fine-grained protection of individual virtual machines without backing up entire namespaces [Src: Kasten Docs 9.0.2 p.347]. The process of restoring virtual machine backups is similar to restoring any other application using the Veeam Kasten dashboard [Src: Kasten Docs 9.0.2 p.544]. Restore points even record the difference, carrying a backup type category of virtualMachine for virtual-machine-based backups or namespace for namespace-based ones [Src: Kasten Docs 9.0.2 p.718].

Do not let the familiarity carry you too far, though. Virtual machines can only be restored into a new namespace [Src: Kasten Docs 9.0.2 p.417]. The in-place restore you would reach for out of habit is not on the menu for that object type.

Across clusters · 03

Moving an application to another cluster

At overview depth: how an export policy on one cluster and an import policy on another combine into a path that lands a running application somewhere it has never run. By the end of this section you can name the four stages, say which policy setting decides whether the path works at all, and explain what an import policy does when nobody has asked for a restore yet.

The workflow for exporting applications into another cluster is close to the workflow for protecting them: when a policy is created to capture an application, you also select the Enable Backups via Snapshot Exports option, and one export action is created for each backup action when the export schedule triggers. Once all the export actions finish for that scheduled time, the metadata is uploaded to the location specified by the profile, and after that upload the backups are available for import [Src: Kasten Docs 9.0.2 p.455].

That "available for import" is the hinge. Nothing about the export knows which cluster will consume it. Location profiles are also used for importing applications into a cluster that is different from the source cluster where the application was captured [Src: Kasten Docs 9.0.2 p.338] — the shared location is the whole handshake, plus one encoded string.

Stage 04 — Restore, then or later. After the Create Policy button is clicked the system starts scheduling jobs based on the policy definition; when new data is detected its metadata is imported into the cluster, associated with the application stack already running, and made available as a restore point [Src: Kasten Docs 9.0.2 p.464]. Unless Restore after Import is selected, only metadata is brought into the cluster, and data volumes residing in an object store or file store are not converted into native volumes until a restore operation is initiated [Src: Kasten Docs 9.0.2 p.464]. From there the normal restore workflow applies, and when given the choice you select a restore point tagged with the import policy name [Src: Kasten Docs 9.0.2 p.464].
Heads up

Care should be taken when auto-restoring the application during import: ensure the newly restored application does not conflict with the application running in the source cluster, and examples of potential conflicts include accidental credential reuse, access to and use of external services, and services conflicting for exclusive ownership of shared resources [Src: Kasten Docs 9.0.2 p.462]. Two live copies of the same application, both convinced they own the same external queue, is a failure mode you cause rather than suffer.

Two behaviours that make an import policy more than a copy

Retention follows the source

Running an import policy keeps the list of local restore points in sync with the retention settings of the originating policy. If a restore point is marked for retirement by the source cluster it is cleaned up, and the next time the import policy runs that retired restore point is removed from the destination cluster, reflecting the fact that it can no longer be used to restore the application [Src: Kasten Docs 9.0.2 p.464].

Resources can be reshaped on the way in

By default Veeam Kasten restores Kubernetes resources as they exist in the restore point, but when the restore target does not match the environment of the backup, resource artifacts can be transformed on restore — for example, updating container image URLs or changing storage class settings when moving between cloud providers [Src: Kasten Docs 9.0.2 p.464]. Transforms are applied by enabling Apply transforms to restored resources under Restore After Import [Src: Kasten Docs 9.0.2 p.465].

Same cluster, different namespace, is a restore

Import is for crossing cluster boundaries. The entire application stack can be migrated across different namespaces in the same cluster, and that is covered by the restore workflow rather than by an import policy [Src: Kasten Docs 9.0.2 p.451]. If you find yourself building an import policy to move a namespace inside one cluster, stop and go back to section 02.

For a customer conversation

The documented resiliency strategies give you a clean way to frame cost against recovery time. A Rebuild approach carries a high recovery time and low infrastructure cost, and suits pre-production or smaller organizations with constrained budgets: policies export backups off-site, and after a site loss a new cluster is deployed, Veeam Kasten is redeployed, a location profile is pointed at the off-site repository, and the catalog is imported [Src: Kasten Docs 9.0.2 p.1093]. A Replicate approach carries a medium recovery time and high infrastructure cost and suits production or enterprise workloads: import policies from secondary storage bring restore point data across on a schedule, and transforms can scale workloads down on import so the standby site costs less while it waits [Src: Kasten Docs 9.0.2 p.1093]. The choice is a budget conversation with a technical answer attached, which is a good conversation to be in.

Who can do what · 04

Access control: who can protect and restore what

The instinct to look for a user list inside the product is the one to unlearn here. By the end of this section you can name the four built-in roles and what each one may do, decide whether a person needs a cluster-wide or a namespace-scoped assignment, and create that assignment from the dashboard.

For role-based access control (RBAC), Veeam Kasten builds on Kubernetes ClusterRoles and Bindings, and each deployment includes default Kubernetes ClusterRoles and Roles for authorization of both full and partial administrator personas [Src: Kasten Docs 9.0.2 p.264]. There is no separate account store to manage: a role is a Kubernetes object, an assignment is a binding, and the scope of the binding is the whole security design.

That is the conceptual jump. In your Veeam Data Platform work, "who can restore this" is a property you set on a user inside a console you administer. Here it is a Kubernetes object that a cluster administrator can also see, audit, and change with the same tools they use for everything else on the cluster. Different plumbing, and the same question underneath: who can protect, who can restore, and who can only look.

Making the assignment from the dashboard

The Veeam Kasten role-based access control dashboard can be used to set up varying levels of access to the dashboard and the APIs [Src: Kasten Docs 9.0.2 p.279]. Veeam Kasten allows users to manage Kubernetes access through it, creating Role Bindings as well as Cluster Role Bindings by choosing existing Roles and Cluster Roles or creating new ones [Src: Kasten Docs 9.0.2 p.280]. Pro tip

Service accounts are bound through the same form, using a naming convention rather than a separate control. Bindings are available for the subject types Users and Groups; where a service account binding is required, the format system:serviceaccount:<sa_namespace>:<sa_name> is used in the User field for a single service account in a specific namespace, or the format system:serviceaccounts:<sa_name> is used in the Group field for a service account in all namespaces [Src: Kasten Docs 9.0.2 p.280].

Heads up

Granting people the ability to manage access is a bigger grant than it looks. Viewing and managing Veeam Kasten-specific Kubernetes RBAC resources from the dashboard requires additional permissions, and while a read-only view can be granted with list and get verbs, additional verbs such as create, update, and delete should be added with caution because they allow those users to escalate their own privileges [Src: Kasten Docs 9.0.2 p.277][Src: Kasten Docs 9.0.2 p.278].

Where the boundaries land in practice

Two scoping facts are worth carrying into your first design. Cluster-scoped restore points sit outside the namespace model: access to a ClusterRestorePoint is reserved for users with Veeam Kasten administrative privileges through Kubernetes RBAC, because the resources are cluster-scoped [Src: Kasten Docs 9.0.2 p.718]. And the direction of travel is worth planning for rather than resisting — the documented guidance is to consider implementing multi-tenancy and turning Veeam Kasten into a backup-as-a-service model rather than restricting its usage to a select group of trusted users, which enables user management based on the principle of least privileges while also supporting self-service [Src: Kasten Docs 9.0.2 p.1092].

Read that guidance as a job description change. Under it, application teams create and manage their own backup policies, set schedules, and determine retention settings [Src: Kasten Docs 9.0.2 p.1092], and your role moves from operating every job to designing the guardrails those teams work inside. The routine in the next section is what that role looks like day to day.

The routine · 05

The daily and weekly routine

Everything above is a thing you do once. This is the thing you do forever. By the end of this section you can walk the dashboard in a fixed order, find failures faster than they find you, and hold a weekly and monthly rhythm that includes the one task everybody skips — testing a restore.

Start with where the answers live. The top of the Veeam Kasten dashboard displays a list of applications, currently mapped to namespaces, any policies that exist in the system, and a summary of the cluster's backup data footprint; after filtering to applications that have stateful services, each section breaks down into Unmanaged, Non-compliant, Compliant, and Removed [Src: Kasten Docs 9.0.2 p.301]. Choosing one of those buttons filters the applications automatically [Src: Kasten Docs 9.0.2 p.301], which makes "show me everything that is not protected" a single click rather than a report.

Below the policy management section you will find activity data: a graph of all activity in the system, where mousing over the graph displays action information such as status, action duration, action start time, and action completion time [Src: Kasten Docs 9.0.2 p.311]. The same information appears in tabular form under the graph, beginning with a summary of total actions, average action duration, the number of data artifacts and their size, followed by recent actions including the policy that generated each one, the number of child actions, the number of applications included in the run, and start and completion times [Src: Kasten Docs 9.0.2 p.311]. You can filter those actions by originating policy, type of action, failed actions, and completed actions [Src: Kasten Docs 9.0.2 p.311] — and the failed-actions filter is your morning.

Alerts surface separately. An alert notification appears in the upper right corner of the dashboard, and clicking the alert icon opens a side pane containing a list of outstanding errors and warnings, each with a description of what went wrong [Src: Kasten Docs 9.0.2 p.490]. Check the corner before you check the graph.

The Restore Points page is your housekeeping surface

The interface has a centralized view listing all restore points created or imported by the cluster, reached from the Restore Points item in the left side menu [Src: Kasten Docs 9.0.2 p.304]. Its filtering is what makes it a weekly tool rather than a lookup. Filtering by type lets you identify local snapshot-based restore points, exported restore points managed by the cluster, or imported restore points created by another cluster; selecting Include manual runs only lists the restore points created by backup or export actions that are not associated with a policy, or by manually running a policy; and selecting No expiration lists those manually created restore points that have no specified expiration date, which allows simple identification and removal of orphaned backup data [Src: Kasten Docs 9.0.2 p.306]. Restore points can be deleted in bulk by selecting them first, or individually from the action dropdown menu [Src: Kasten Docs 9.0.2 p.306], and local restore points can be exported from that dropdown while exported restore points can be validated from it [Src: Kasten Docs 9.0.2 p.305].

Remember

Pair those two filters together — manual runs only, no expiration — and run it weekly. Artifacts from manual runs are outside the policy's retention schedule and must be cleaned up manually [Src: Kasten Docs 9.0.2 p.364], and that pair of filters is how you find the ones you forgot. Nothing else on the dashboard will nag you about them.

Test restores, on purpose, on a schedule

The strongest operational guidance in the documentation is also the easiest to postpone: test restores regularly and do not wait for a disaster to happen, testing application restores within the same namespace, in a different namespace on the same Kubernetes cluster, and on different clusters [Src: Kasten Docs 9.0.2 p.1093]. Test granular application restores as well as full application restores, and restore applications based on priority to meet recovery time objective (RTO) requirements [Src: Kasten Docs 9.0.2 p.1093]. Those three destinations map exactly onto the three paths in section 02, which is a convenient way to build a rotation: same namespace this week, new namespace next week, another cluster the week after.

Policy and retention hygiene worth scheduling

Bias retention outward

To optimize storage costs, the documented recommendation is to reduce local retention, which can be more expensive, and increase remote retention, and to strike a balance that prevents storage from filling up [Src: Kasten Docs 9.0.2 p.1092]. Shorter on snapshots and extended periods for exports is the same advice from the policy side [Src: Kasten Docs 9.0.2 p.1093].

Do not protect with a wildcard

Avoid creating a policy with a wildcard namespace selector; create policies per application or per application group and use the backup window and staggering instead, which reduces load on both Veeam Kasten and the cluster API [Src: Kasten Docs 9.0.2 p.1093]. Define a backup window that does not conflict with multiple policies, to prevent system overload [Src: Kasten Docs 9.0.2 p.1093].

Standardize, then delegate

Use a policy preset to standardize backup and export retention across policies, configure a dedicated policy for protecting cluster-scoped resources, and use labels to target specific resources so one policy can serve a group of them [Src: Kasten Docs 9.0.2 p.1093]. Presets are what make self-service safe: each policy created from a preset refers to it rather than copying it, so every preset change also changes the corresponding policies [Src: Kasten Docs 9.0.2 p.384].

Check application readiness

Regularly verify the readiness of your applications; if they are scaled down, experiencing issues, or not functioning correctly, enabling the "Ignore Exceptions and Continue if Possible" option in the policy actions ensures they are carried out to the best of their ability [Src: Kasten Docs 9.0.2 p.1093].

Let the metrics do the watching

Veeam Kasten provides metrics about its activities; the documented approach is to gather them with Prometheus to track backups, restores, and overall system health, visualize them in Grafana, and configure alerts when metrics exceed critical levels [Src: Kasten Docs 9.0.2 p.1093]. Creating alerts for any actions where state=failed is recommended, along with an alert for catalog volume used space above 50 percent, because that condition can affect upgrades [Src: Kasten Docs 9.0.2 p.1093].

Keep looking, and keep the monitoring current

Regularly check the metrics and logs of your Veeam Kasten system, which helps you find and fix problems before they lead to downtime or data loss, and keep the monitoring configuration up to date as the deployment evolves so you monitor the right metrics and receive alerts for new issues [Src: Kasten Docs 9.0.2 p.1093].

Did you know?

There is a guided walkthrough of the dashboard built into the product. An interactive tour is available when the dashboard is accessed for the first time, or afterwards via the Interface page of the Settings menu in the navigation sidebar [Src: Kasten Docs 9.0.2 p.301]. Worth 10 minutes on day one, and worth pointing an application team at when you hand them their namespace.
