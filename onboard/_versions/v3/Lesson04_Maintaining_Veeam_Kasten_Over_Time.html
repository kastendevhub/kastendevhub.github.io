Overview · 01

Day two: you now own the protector

This section maps the maintenance routine you already run for Veeam Data Platform onto Veeam Kasten, so the rest of the module has somewhere to attach. By the end of it you'll be able to name the Veeam Kasten equivalent of patching, job-health checking, and configuration backup — and say where each parallel stops being useful.

As a Veeam Data Platform administrator you have a rhythm. You patch the backup server on a schedule you control. You open the console in the morning and read job sessions. You keep a configuration backup, because the catalog of what you protect is worth more than any single restore point. Veeam Kasten asks for the same three habits, in a different shape: the product is a set of services running inside the cluster it protects, upgraded with the same Helm release you installed it with, observed through metrics rather than a console you keep open, and protected by a policy it creates for itself.

Two differences change the calendar more than anything else in this module. First, cadence: Veeam Kasten ships far more frequently than a Veeam Data Platform release cycle — the product documentation's own maintenance guidance is to always upgrade and not stay on an outdated version for comfort, noting releases every two weeks [Src: Kasten Docs 9.0.2 p.1093]. Second, the floor moves: Veeam Kasten supports a defined list of Kubernetes and OpenShift versions and does not support distribution versions that are no longer actively supported by their vendor or community [Src: Kasten Docs 9.0.2 p.861], so a cluster upgrade you do not own can put your backup platform out of support.

Two ideas to carry through this module

Everything that follows — upgrades, monitoring, catalog protection, housekeeping — falls out of these two.

Upgrades · 02

Upgrading Veeam Kasten, and keeping pace with the cluster

This section gives you the upgrade rules, the command that performs the upgrade, and a planner you can use to decide whether your instance is one hop or several hops from current. It also covers the version support you do not control: the Kubernetes and OpenShift releases underneath you.

The two rules that decide your upgrade plan

Veeam Kasten upgrades are supported across a maximum of four versions (for example, 2.0.10 to 2.0.14). If your instance is further behind, a step upgrade process is recommended, using the --version flag with helm upgrade to control the version jumps — and at least 50% free space is required in catalog storage [Src: Kasten Docs 9.0.2 p.198].

You do not have to work the arithmetic out by hand. You can verify available catalog free space and see your recommended upgrade path from the System Information page under the Settings menu in the navigation sidebar [Src: Kasten Docs 9.0.2 p.198]. From a terminal you can ask the same question with k10tools — get the binary before you need it, since it is a separate download rather than something the Helm chart installs for you: Veeam Kasten publishes k10tools for Linux, macOS, and Windows, and the current release is linked from the Veeam Kasten Tools page in the product documentation [Src: Kasten Docs 9.0.2 p.866]. Its k10tools primer upgrade sub-command finds the recommended upgrade path for your version and checks there is adequate space, for Helm deployments — and it requires internet access to gcr.io, so on a restricted or air-gapped cluster the System Information page is the route that still works [Src: Kasten Docs 9.0.2 p.872].

shell 
./k10tools primer upgrade
Catalog space is the constraint people trip over. A release may perform a catalog schema upgrade, and the schema upgrade requires at least 50% of free space in the catalog-pv-claim persistent volume — the claim's size may need to be increased first. Available catalog storage space is visible in the dashboard under Settings > System Information > Upgrade Status [Src: Kasten Docs 9.0.2 p.1097].

The upgrade itself

An upgrade is a Helm upgrade of the release you installed, run against the namespace you installed into — the documented example assumes the kasten-io namespace and the release name k10 [Src: Kasten Docs 9.0.2 p.199]. The documented sequence refreshes the chart repository, captures your current values, and upgrades using them, so your configuration survives the upgrade [Src: Kasten Docs 9.0.2 p.200].

shell · upgrade to the latest release 
helm repo update && \
  helm get values k10 --output yaml --namespace=kasten-io > k10_val.yaml && \
  helm upgrade k10 kasten/k10 --namespace=kasten-io -f k10_val.yaml

For a step upgrade, the same sequence carries a pinned version — this is the form the upgrade primer prints as its recommended upgrade path, with the target release on the end [Src: Kasten Docs 9.0.2 p.872].

shell · one hop of a step upgrade 
helm repo update && \
  helm get values k10 --output yaml --namespace=kasten-io > k10_val.yaml && \
  helm upgrade k10 kasten/k10 --namespace=kasten-io -f k10_val.yaml --version=4.5.6
Heads up

Read the Upgrade Notes for every release you pass through, not only the one you land on — that is where the breaking details live. Recent examples: an app_namespace label was added to per-application metrics, so Prometheus queries that pin the exact label set may need updating [Src: Kasten Docs 9.0.2 p.1097]; metrics sourced through Red Hat ACM Observability moved from cluster_id to cluster_uid, so dashboards and alert rules filtering on the old label need changing [Src: Kasten Docs 9.0.2 p.1099]; and policy, profile, and action names became limited to 63 characters, with names above that rejected at creation time [Src: Kasten Docs 9.0.2 p.1099]. If Generic Storage Backup is in use and a new Kanister-tools image ships, extra steps may be needed to update the Kanister sidecar image [Src: Kasten Docs 9.0.2 p.200].

Keeping pace with Kubernetes

The other half of staying current is the platform underneath. Veeam Kasten publishes the certified Kubernetes distributions and respective OpenShift versions it supports, and does not support distribution versions that are no longer actively supported by their vendor or community [Src: Kasten Docs 9.0.2 p.861]. A single Veeam Kasten release can move both ends of that list: release 8.5.9 added support for Kubernetes 1.34 [Src: Kasten Docs 9.0.2 p.1098] and, in the same release, removed support for Kubernetes 1.30 while OpenShift 4.17 clusters continued to be supported [Src: Kasten Docs 9.0.2 p.1099].

Pro tip

Put the cluster's Kubernetes upgrade on the same calendar as the Veeam Kasten upgrade, and sequence them deliberately. Veeam Kasten supports a published list of Kubernetes and OpenShift versions and does not support distribution versions that are no longer actively supported by their vendor or community [Src: Kasten Docs 9.0.2 p.861, p.862], and a single release can add one version and remove another [Src: Kasten Docs 9.0.2 p.1098, p.1099] — so if the platform team moves the cluster first, your options narrow to whichever Veeam Kasten release supports the new version, while upgrading Veeam Kasten first keeps the choice. This is the coordination cost a Veeam Data Platform administrator does not carry when the backup server owns its own Windows host. Put a name on it: agree with the platform team, in writing, who has to sign off before a cluster upgrade proceeds if it would drop the running Veeam Kasten release out of the supported matrix — otherwise the backup platform loses support status by nobody's decision.

Monitoring · 03

Watching Veeam Kasten itself

This section takes you from the morning glance to the support case: the three layers of monitoring available to you, the alerts worth creating first, and the order to gather diagnostics in when something looks wrong.

Layer one: the dashboard

The top of the Veeam Kasten dashboard shows the applications on the cluster, the policies that exist, and a summary of the cluster's backup data footprint [Src: Kasten Docs 9.0.2 p.301]. Filtered to applications with stateful services, each is placed in one of four states — the closest thing here to your morning read of job sessions [Src: Kasten Docs 9.0.2 p.301].

Unmanaged

No protection policy covers this object [Src: Kasten Docs 9.0.2 p.301].

Non-compliant

A policy applies, but its actions are failing or have not been invoked yet — for example, right after policy creation [Src: Kasten Docs 9.0.2 p.301].

Compliant

A policy applies and its service-level agreements (SLAs) are being respected [Src: Kasten Docs 9.0.2 p.301].

Removed

Objects that no longer exist on the cluster; filter to this state to find a removed application and restore it [Src: Kasten Docs 9.0.2 p.301, p.397].

Layer two: the built-in Prometheus instance

Veeam Kasten enables centralized monitoring of its activity by integrating with Prometheus, exposing a Prometheus endpoint that a central system can extract data from [Src: Kasten Docs 9.0.2 p.746]. The built-in instance is configured by default with persistent storage of 8Gi and a retention period of 30d, changeable through the prometheus.server.persistentVolume.size and prometheus.server.retention Helm values [Src: Kasten Docs 9.0.2 p.746].

Leave that server enabled. Disabling it reduces functionality in various parts of the system, including usage data, reporting, and the multi-cluster dashboard; if it has been disabled, it can be re-enabled during a Helm upgrade with --set prometheus.server.enabled=true [Src: Kasten Docs 9.0.2 p.763].

Action metrics are the ones you will query first. Veeam Kasten records counts for cluster and application-specific actions, labels them with the action's context, and includes the final status as state for ended actions — with an action's state reported as values including pending, running, attempt_failed, failed, succeeded, cancelled, skipped, and deleting [Src: Kasten Docs 9.0.2 p.748].

PromQL · successful backups in the past 24 hours 
sum(round(increase(action_ended_total{action="backup",state="succeeded"}[24h])))

Read it as: how many backup actions finished successfully in the last 24 hours. action_ended_total is the metric name; the curly braces filter to backup actions that succeeded; [24h] is the lookback window; increase counts how many happened inside it; sum and round collapse that down to one tidy number.

Swap the labels and you have the query that matters more: sum(round(increase(action_ended_total{action="restore",state="failed"}[1h]))) returns failed restores in the past hour [Src: Kasten Docs 9.0.2 p.748].

Layer three: your existing monitoring stack

Metrics can leave the cluster two ways: Prometheus remote write pushes them to remote Prometheus-compatible endpoints such as Grafana, Datadog, or Thanos, and external Prometheus integration has an outside Prometheus instance scrape the built-in server — remote write is documented as the recommended route for most use cases [Src: Kasten Docs 9.0.2 p.754]. Grafana then visualizes what Prometheus collected, and alerts fire when metrics cross the levels you care about [Src: Kasten Docs 9.0.2 p.1093]. In most organizations that central Prometheus/Grafana stack belongs to a platform or observability team rather than the backup team — name who owns wiring the two alerts this module recommends (failed actions, catalog space over 50%) before you assume they already exist.

The two alerts to create first. The product's own guidance is to create alerts for any actions where state=failed, and for Catalog Volume Used Space > 50%, because that condition could impact Veeam Kasten upgrades [Src: Kasten Docs 9.0.2 p.1093]. The second one is the link back to Section 02: the alert that protects your upgrade window. For version tracking from an external monitor, the k10_build_info Prometheus gauge metric exposes the running Veeam Kasten version as a label [Src: Kasten Docs 9.0.2 p.1099].

Protecting the catalog · 04

Who backs up the backup system?

This is the section your director or CISO will ask about first. By the end of it you'll be able to explain what Veeam Kasten Disaster Recovery protects, choose a mode based on what your storage can do, and describe the recovery path from an empty cluster back to a working catalog.

Veeam Kasten is a stateful application running on the cluster, so it must be responsible for backing up its own data to enable recovery in the event of disaster — the backup enabled by the Veeam Kasten Disaster Recovery (KDR) policy [Src: Kasten Docs 9.0.2 p.565]. KDR provides the ability to recover the Veeam Kasten platform from a variety of disasters: unintended deletion of Veeam Kasten or its restore points, failure of the underlying storage used by Veeam Kasten, or accidental destruction of the Kubernetes cluster Veeam Kasten is deployed on [Src: Kasten Docs 9.0.2 p.565]. The API exposes the same capability as a KastenDR object, whose resources fetch the list of available KDR restore points and restore an instance from one [Src: Kasten Docs 9.0.2 p.620].

The Veeam Data Platform parallel is configuration backup, and it holds up well: both protect the metadata that makes restore points findable, both are scheduled, and both are worthless if you cannot decrypt them. Where it breaks is the dependency list. The guide is blunt about what to retain after enabling KDR, without which restore point catalog recovery will not be possible: the source Cluster ID, the KDR passphrase or the external secret manager details, and the KDR location profile details and credential [Src: Kasten Docs 9.0.2 p.585].

Two constraints to settle before you enable it. Choose a location profile that supports immutable backups — the guide states this strongly, so that restore point catalog data can be recovered in the event of incidents including ransomware and accidental deletion [Src: Kasten Docs 9.0.2 p.571]. And check your intended target: Veeam Repository location profiles cannot be used as a destination for KDR backups [Src: Kasten Docs 9.0.2 p.572]. Passphrase options include a passphrase you supply, HashiCorp Vault, and AWS Secrets Manager [Src: Kasten Docs 9.0.2 p.572]; Azure Key Vault Secrets was added as a passphrase provider for Disaster Recovery, allowing KDR passphrase storage and retrieval from Azure Key Vault [Src: Kasten Docs 9.0.2 p.1103].

Choosing a KDR mode

The KDR mode specifies how internal Veeam Kasten resources are protected. It must be set before enabling the KDR policy, and changes to the mode only apply to future KDR policy runs [Src: Kasten Docs 9.0.2 p.565]. Starting in Veeam Kasten v8.0.0, all installations default to Quick DR (Local Catalog Snapshot) mode — a mode that should only be enabled if the storage provisioner used for Veeam Kasten persistent volume claims supports both creating storage snapshots and restoring the existing volume from one [Src: Kasten Docs 9.0.2 p.565].

The policy KDR creates for you

Enabling KDR creates a dedicated policy that backs up Veeam Kasten's resources and catalog data to an external location profile [Src: Kasten Docs 9.0.2 p.571]. That policy is named k10-disaster-recovery-policy, is created automatically when KDR is enabled, and can be viewed through the Policies page in the navigation sidebar; Run Once starts a manual backup, and Edit changes the frequency and retention [Src: Kasten Docs 9.0.2 p.587]. The frequency guidance is worth writing down: the KDR policy should match the frequency of the lowest recovery point objective (RPO) policy on the cluster [Src: Kasten Docs 9.0.2 p.587].

For a customer conversation

"Who backs up the backup system?" is the question that ends a lot of Kubernetes protection projects late. The answer here is concrete and demonstrable: the platform runs a dedicated policy over its own namespace, exports the catalog to an external location profile you choose — one that supports immutable backups, so the catalog survives ransomware and accidental deletion — and encrypts it with a passphrase held in a passphrase provider, then recovers onto a new cluster from that export [Src: Kasten Docs 9.0.2 p.565, p.571, p.1093].

Housekeeping · 05

Housekeeping, and a healthy week in the life

The last section covers the cleanup Veeam Kasten does on its own, the space behavior that surprises people, and a maintenance rhythm you can put on a calendar this week.

Veeam Kasten provides a way to collect and clean up resources that are either orphaned or whose expiration period has passed, through a garbage collector daemon [Src: Kasten Docs 9.0.2 p.839]. Three Helm options tune it: garbagecollector.daemonPeriod sets the length of time between two consecutive garbage collection events in seconds, garbagecollector.keepMaxActions sets how many finished actions to keep — with no actions deleted if the value is less than or equal to zero — and garbagecollector.actions.enabled enables the action collectors [Src: Kasten Docs 9.0.2 p.839].

What the daemon cleans is a specific list: actions above the retained maximum, oldest first and handled independently per action type; RestorePointContents for expired manual backups, as determined by their expiresAt value; and the temporary objects left behind by restore operations — CSISnapshot objects, persistent volumes, profiles, services, network policies, secrets, and config maps [Src: Kasten Docs 9.0.2 p.839]. Export pods are cleaned up by the garbage collection daemon after the configured grace period [Src: Kasten Docs 9.0.2 p.1097].

Retiring a restore point does not mean the space comes back today. When restore points are retired — manually or through a policy retention schedule — Veeam Kasten cleans up the associated resources, but the cleanup is not immediate for all of them; backup data in an object store may take a significant amount of time to be removed [Src: Kasten Docs 9.0.2 p.365]. Data references shared between restore points, aggregated data awaiting garbage collection, version retention for immutable backups, and safety windows for re-referencing data are among the reasons a retirement might not immediately free space, and deduplication can mean minimal or no reclamation at all [Src: Kasten Docs 9.0.2 p.365]. If you have ever explained to a storage owner why deleting backups did not return capacity, you have given this speech before.

Log volume is the other thing worth setting deliberately. Log retention is tuned with Helm values including a rotation count and a size threshold that triggers rotation, applied during an upgrade of the release [Src: Kasten Docs 9.0.2 p.176].

shell · tuning log retention 
helm upgrade k10 kasten/k10 -n kasten-io --reuse-values \
  --set logging.retention.rotateCount=12 \
  --set logging.retention.maxFileSize=2G

    Confirm the KDR policy is running to schedule [Src: Kasten Docs 9.0.2 p.587], and check catalog storage space against the 50% mark [Src: Kasten Docs 9.0.2 p.1093].
  3. 3
    Monthly
    Test restores rather than waiting for a disaster — in the same namespace, a different namespace, and a different cluster [Src: Kasten Docs 9.0.2 p.1093] — and test the KDR process itself [Src: Kasten Docs 9.0.2 p.1093].
  4. 4
    Quarterly
    Plan the next upgrade hop, and review the supported Kubernetes and OpenShift matrix against the cluster's roadmap [Src: Kasten Docs 9.0.2 p.198, p.862].
  • Monitoring configuration is reviewed as the deployment evolves, so you are watching the right metrics and getting alerts for new issues [Src: Kasten Docs 9.0.2 p.1093].
  • Alerts exist for failed actions and for catalog volume used space, the two conditions the guide calls out [Src: Kasten Docs 9.0.2 p.1093].
  • The KDR passphrase is retrievable by someone other than you, from a passphrase provider rather than a personal note [Src: Kasten Docs 9.0.2 p.572]. Decide who that second person or team is — security, a fellow backup admin, the secrets-management team — and write it into the runbook; "someone other than you" is a decision your team has to make explicitly, not a default the product supplies.
  • The upgrade path is known before the upgrade window opens, from the System Information page or the upgrade primer [Src: Kasten Docs 9.0.2 p.198, p.872].
